## 1. Executive Summary

Legatium is a small library — about 2,200 lines of Kotlin code once comments are removed — that logs one structured line per outbound HTTP call for two Spring client stacks, with a documented fail-open contract, an index-side field contract and six meters. Measured against that problem, the **architecture fits**: the module cut (one shared layer inlined into two stack-specific twins) follows the real seam of the domain (blocking `RestClient` versus reactive `WebClient`, two genuinely different body-tee and emission designs), the injectable collaborators are real seams with real second implementations or a determinism need, the reactive complexity in the WebClient twin is load-bearing, and every non-obvious decision has an ADR with a rationale. There is **no under-engineering**: boundaries exist where the domain has them, logic is separable from I/O everywhere, and the fail-open discipline is centralised in two shared guard shapes rather than scattered.

The tendency, where there is one, is toward **over-investment in the twin's mirror image and in prose**. The "deliberately duplicated remainder" that ADR-0003 reserves for copies that *genuinely differ* has, in three places, converged to near-identity: the two metrics classes are 95 % identical, the activation logic is 96 % identical, the auto-configurations 74 % — and the running cost is visible in the project's own history, where the same change was applied twice in both directions within one day and once diverged. The documentation mirrors the same shape: two 1,350-line guides that share 786 identical lines, twin READMEs at 65 % similarity, and 4,400 lines of documentation for 2,200 lines of code, so that a cross-cutting change is written three times (two guides, a README pair) before it is done. The biggest structural risk is therefore not a wrong abstraction but **drift between mirrors** — the class of defect the same-day analysis actually found (a guard present in one twin and not the other), which the lockstep tests catch only for *named* contracts.

The delivery machinery — twelve Maven plugins, six workflows, four generator scripts, SBOM, SLSA provenance, fuzzing, a docs site with generated test evidence — is heavy for the code mass but is the ecosystem's shared template (documented in the user's project setup rules) and serves a published Maven Central artifact in a regulated-evidence context: a justifying force, not a finding. Likewise the Shade inlining with compiler friend paths is an ADR-backed trade whose costs are now written down; it deserves a re-evaluation before the first release rather than a correction now.

**Test verdict.** *Testability of the architecture:* excellent — time, ids and masking are `fun interface` seams with hand-written fakes (no mock library in the repository), the interceptor and the filter are constructed directly and driven with stub executions and stub responses, every signal of the reactive lifecycle can be produced synchronously, and the fail-open paths are reachable through hostile registries and appenders without a container. *Utilization and shape:* healthy and matching — 272 tests of which only five classes boot a Spring context and two use a context runner, all of them where the subject *is* the container or a real engine; the reactive twin's tests exercise the reactive contract itself (`StepVerifier`, a `BaseSubscriber`, a manual publisher) rather than blocking around it. *Most significant gaps and anomalies:*
- a hand-assembled class-file generator (`NettyNamedTimeout`, 89 lines of constant-pool arithmetic) exists to avoid one test-scoped dependency — gold-plated infrastructure for two assertions;
- the twin test helpers are duplicated by design (`PeerServer` byte-identical, `TestSupport`, `TwinContractTest`, the auto-configuration tests at 70–100 % similarity) under the ADR's "copies are cheaper than a test-jar" rule — justified, but it doubles the mirror-drift surface into the tests;
- the integration layer's real-time dependence (a sleeping peer, a Linux-specific tarpit) is documented and confined — an accepted cost of testing four real engines, not an architecture symptom.

## 2. Problem Baseline & Methodology

- **What the system does.** Two Spring Boot auto-configured libraries that attach to every outbound `RestClient`/`RestTemplate` call (blocking twin) or `WebClient` call (reactive twin) and emit one structured `adapter_*` log line per exchange plus six Micrometer meters, with the identity contract of ADR-0002 (`traceparent` trace id as request id, correlation header on traceless calls), masked header sections (ADR-0005), outcome-gated body capture (ADR-0006) and a fail-open contract (a logging failure must never affect the call). It is the outbound counterpart of the sibling project limesium (inbound), and the two are designed to join in one log document.
- **Masses.** Production Kotlin: 4,142 lines, of which 2,214 code, 1,647 comment (43 %) and 281 blank; per module 1,100 / 1,488 / 1,554. Tests: 7,534 lines, 272 tests (76 / 97 / 99). Documentation: 4,403 lines (two guides 2,706, module READMEs 484, root README 118, seven ADRs 509, reference YAML 163, ELK 143, CONTRIBUTING 155, CHANGELOG 109). Configuration surface: 17 property keys in one shared class; 13 log fields in one shared enum; 6 meters; 3 `fun interface` seams.
- **Real requirements and scale.** A library on the hot path of every outbound call of a host — per-call overhead and allocation matter, wall-clock latency does not (no SLA is stated or implied). Two stacks are a *real* requirement (hosts use either or both). The index-side field names, the meter names and the configuration keys are contracts with dashboards and the sibling project — contract stability is a real force. No persistence, no messaging, no multi-tenancy, no scale target beyond "a host's call volume".
- **Team and maturity.** One developer (25 commits, all by one author, over two days: 2026-09-03 to 2026-09-04); version `1.0.0-SNAPSHOT`, nothing released; the CHANGELOG has an "Unreleased" section only. The project is one of a family built from a shared template (the user's global project-setup rules name `tabellarium` as the reference and `limesium` as the multi-module example) — the delivery pipeline is inherited, not invented here.
- **Documented architectural intent.** Seven ADRs, each with a Decision and Consequences: ADR-0001 (fuzz signal), ADR-0002 (trace id is the request id), ADR-0003 (shared code inlined by Shade; what stays duplicated and why; two amendments moving byte-identical classes to the shared module; a same-day amendment stating the no-relocation consequences), ADR-0004 (counting correlation id — the rationale is explicitly *structural*, not measured: "the latency is unlikely to be visible"), ADR-0005 (masked by default), ADR-0006 (bodies by outcome), ADR-0007 (the `adapter` vocabulary). CONTRIBUTING fixes the test conventions (Given/When/Then, rationale block, no mock libraries implied by practice, Jazzer targets in Java) and the "build from the root" constraint. These are treated as justifying forces throughout; code was checked against them, not against an external ideal.
- **Technology coherence.** The blocking twin is blocking end to end (interceptor, `InputStream` tee, thread-local MDC scope); the reactive twin is reactive end to end (`ExchangeFilterFunction`, `DataBuffer` tee through a decorator, a body operator on the terminal signal, no thread-local state around the call). Neither mixes paradigms; the reactive stack exists because `WebClient` is reactive, not by choice. No coroutine code in production (documented as the same filter). The shared layer is paradigm-neutral.
- **Test topology observed.** Pyramid, healthy: 272 tests; unit suites construct the interceptor/filter directly with an injected `AtomicLong` clock, a pinned id generator and stub executions/responses; five `@SpringBootTest` classes (two per twin for a real engine and a real tracing bridge, plus the four-engine contract in the reactive twin sharing one cached context) and two `ApplicationContextRunner` classes for the auto-configuration contract; three Jazzer targets with seed corpora; no mock library anywhere. Infrastructure per typical test: none. Infrastructure per integration test: an in-process JDK `HttpServer` peer, a real connector, one Spring context (cached).
- **Analyzed vs. not analyzed.** All three modules' production code and tests, the build and the delivery pipeline as means; not analyzed: the sibling project limesium (referenced only where the twins' parity is the stated force), the docs-site rendering itself.
- **Known blind spots.** (a) Runtime cost claims (allocation per call, the id generator's structural argument) were not measured — no benchmark exists in this repository and none was run; (b) the "both twins in one host" deployment cannot be observed inside the reactor; (c) consumer feedback on the one-artifact convenience of ADR-0003 is unknowable pre-release.

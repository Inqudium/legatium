## 1. Executive summary

In the style sense this is a mature, disciplined Kotlin codebase. Formatting is tool-owned (ktlint official style, green in every build), the language is used the way it is meant to be — `fun interface` seams, `require`/`check` for invariants, `when` expressions, `object` for constants, extension functions for the builder overloads, `internal` on 28 of 41 top-level declarations, string templates throughout, no `!!` in production code, no wildcard imports, no TODO debt, no non-English text. The degree of "Java in Kotlin" is close to zero: three call sites use JDK statics where Kotlin has the idiom (`java.lang.Long.toUnsignedString`, `Math.ceil`), and that is the whole list. Spring is used idiomatically as well: constructor-only wiring, `@ConfigurationProperties` on a validated data class, `@ConditionalOnMissingBean` seams, no field injection anywhere in production code.

The findings are consequently about **consistency and public-API polish** rather than about idiom. The one High-rated item is a documented project convention that half of the test suite does not follow: CONTRIBUTING requires a three-line rationale block at the top of every test body, and 133 of 269 tests lack it — the block is what the generated test-evidence page shows, so the deviation is visible to every reader of the docs site. The Medium cluster is small and concrete: the public `DEFAULT`/`SYSTEM` companion members are not Java-friendly (the project's own Java fuzz test has to write `HeaderValueMasker.Companion.getDEFAULT()`), three closed vocabularies are string constants while the codebase models every other closed set as an enum with a `tagValue`, one class is public in one twin and internal in the other, the three JDK statics named above, and four functions of 94–140 lines in the two entry points and emitters. The Low items are polish: a stylistic divergence between the two emitters, a `var` rebuild chain, `!!` in fifteen test lines, one `assertThatThrownBy` among sixty-one `catchThrowable`s, an implementation class nested inside a companion object, and a duplicated predicate in a Java test.

The house style has a recognisable voice — dense constraint comments with capitalised emphasis words (`ONE`, `NOT`, `BEFORE`, ~150 occurrences), `should …` test names in backticks throughout, AssertJ only, hand-written fakes only, Given/When/Then in 98 % of tests — and it is applied uniformly enough that consistency, not doctrine, is the yardstick that produced most of the findings.

## 2. Baseline & methodology

**Enforced rules (authority 1).**
- `ktlint` 1.8.0, `ktlint_official` code style, `ktlint:check` bound to `verify` — formatting, import ordering, trailing commas, chained-call wrapping, blank-line and indentation rules are tool-owned and green; nothing in that area is reported by hand.
- `./.editorconfig`: UTF-8, LF, 4-space indentation for Kotlin, `max_line_length = off` (so long lines are deliberately unconstrained — not a finding).
- No detekt, no ArchUnit, no Sonar. Their absence is noted; the manual read covers what detekt would (complexity, naming, magic numbers) — see finding 6 and the pattern section.

**Documented conventions (authority 2).** `./CONTRIBUTING.md`: match the surrounding comment density and naming; comments state constraints the code cannot express; test classes `*Test.kt`; the three-line rationale block (`What is tested:` / `Success criteria:` / `Why it matters:`) at the top of every test body followed by `Given/When/Then` stage comments; fuzz targets in Java. `./docs/adr/ADR-0007`: the operator-facing vocabulary is `adapter`, code names keep their `Client*` form — so `ClientRequestLoggingInterceptor` beside `adapter_*` fields is a decided convention, not a naming finding. No English-only rule is written down; the codebase is English throughout, so no deviation exists to report.

**Stack.** Kotlin 2.4.10 (data classes, `fun interface`, `ArrayDeque`, `buildMap`, `HexFormat` available and used), Java 21 in the fuzz targets (switch arrows used), Spring Boot 4.1.1, the `spring` all-open plugin (no manual `open` needed or present).

**De-facto house style (authority 3), derived from the majority of the code:**
- Visibility: `internal` by default (28 of 41 top-level declarations), public only for the host-facing API (properties, the three seams, `MdcKeys`, the two enums, the two entry points, the two auto-configurations).
- Bodies: expression and block bodies in equal measure (42 / 42 by count) — no dominant pattern, so neither is a finding.
- Closed sets: `enum class` with a `tagValue` where a value goes on the wire (`BodyReadState`, `ClientStack`), `enum class` with behaviour (`BodyLogMode`), a typed enum for the field family (`ClientLogField`).
- Immutability: `val` everywhere except `@Volatile` lifecycle state on the `Exchange` holders and lock-guarded capture state — every production `var` is one of those or a loop variable.
- Comments: dense KDoc stating constraints, capitalised emphasis words as a house idiom (~150 occurrences of `ONE`, `NOT`, `BEFORE`, `FIRST`, … via grep; consistent, therefore not a finding).
- Tests: JUnit 5, AssertJ only (no JUnit assertions, no Hamcrest, no mock library), backtick names that are full `should …` sentences (266 of 266), `Given/When/Then` comments (263 of 269), `catchThrowable` for exceptions (61 of 63), `@Nested` grouping in the larger classes (11 of 34 classes), `@Autowired lateinit var` only in the Spring integration tests (Spring's own test idiom).

**Analyzed vs. not analyzed.** All production Kotlin and all test code of the three modules; not analyzed: documentation prose, workflow YAML, the Python scripts.

**Blind spots.** No IDE inspection profile was run; complexity is judged by function length and nesting on reading, not by a metric tool.

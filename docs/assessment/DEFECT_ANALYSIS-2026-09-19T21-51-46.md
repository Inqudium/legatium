## 1. Executive summary

This is the fifth defect analysis of the codebase and the third today. Between the previous report (`DEFECT_ANALYSIS-2026-09-19T20-24-59`, commit `3ccfcdc`) and this commit, all 19 actionable findings of that report were fixed on one branch, two were closed by recorded decision, and every fix was re-verified here as present and effective against the current code (section 2, "Carried items"): the body-meter cache no longer registers a meter under a `ConcurrentHashMap` bin lock (the lock-order deadlock of the previous High is gone - the miss path resolves outside the map and publishes with `putIfAbsent`, pinned by a test with real cross-thread removal), a meter the registry refuses is no longer cached (pinned with a denying filter), the reactive twin's Boot suite no longer shares a mutable builder across tests, the shared buffer's fuzz target has a corpus and a nightly job, and the tail of test-hygiene items is closed. The only production code that changed is the cache's miss path in `ClientLoggingMetrics`; the twins' lifecycle code - bounded body capture, exactly-once completion, fail-open guards, additive MDC and context restoration, twin symmetry - is unchanged and was re-read in full and found sound again.

**No Critical, High or Medium finding remains.** The one production item is a residue of the very fix that closed the High: resolving the meter OUTSIDE the map opens a window of a few microseconds between the registration returning and `putIfAbsent` in which a host `remove` of that same meter runs the listener against an empty cache, after which the detached instance is published and never released - the drift the listener exists to close, for one tag set, silently, and only in a host that removes meters at runtime (Low). Everything else is test quality, all Low: the events counter's "after the level gate" contract is unpinned in both twins, the blocking twin's Boot suite carries an order-dependent absolute counter assertion that is green by hash coincidence today, the consumer smoke test cannot tell "one twin twice" from "both twins once" and waits unboundedly, and four small coverage gaps at documented branches (a cancel-then-response pass-through, the reactive request sample without a response, a throwing masker at wiring, the owner's own diagnostics-channel guard).

**Test verdict.** *Reliability as a safety net:* high across all three modules - the score-5 suites go red under the mutation experiments applied here (the `&&`/`||` flip in the activation short-circuit, the deleted `NoopMeter` check, a key that folds template or host, the removed `updateQuietly` guard, the removed `subscribed` CAS, a stopped tee, the unguarded stream close, a reordered wiring step, the encoding rule inverted), fault injection is real (a JVM-globally armed failing MDC adapter, throwing counters and summaries, a `MeterFilter.map` hook that removes a meter from another thread mid-registration, a body that refuses a second subscription), and the risky logic is checked deterministically with an injected clock and pinned ids. *Usage & coverage:* the pyramid is base-heavy - roughly 430 unit and contract tests carry the behaviour; nine real-engine suites (five request factories, four connectors, including the `exchangeToMono` second-subscription scenario), Boot-builder and Brave tracing integrations and the consumer smoke test verify the seams; all four fuzz targets now run with corpora in regression mode and nightly in fuzzing mode; every wait that crosses a thread in the twins is bounded. *Most significant gaps and anomalies:*

- The events counter - the reconciliation ground truth against the log index - can be moved above the level gate in either twin without a red test (finding 2).
- The blocking twin's Boot suite asserts an absolute `complete` count on a registry shared by eight tests; the two later tests that increment the same tag set sort behind it by JUnit's name hash alone (finding 3).
- The consumer smoke test - the only proof of the shaded jars - accepts two lines from one twin as "one per twin" and blocks without a timeout against a real peer (findings 4, 5).
- The reactive twin's integration awaits remain blind to a surplus event (pattern P3, open by decision, unchanged).

## 2. Scope & methodology

**Modules and roles.** `./legatium-common/` holds the byte-identical shared code the two twins inline through Shade (ADR-0003): the bounded buffer, properties and their origins, header selection and masking, activation, identity (`traceparent`, correlation header, counting id), classification, the metrics owner with the body-meter cache, MDC scope, timeout classification and the observation-wiring report. `./legatium-restclient-logging/` is the blocking twin (a `ClientHttpRequestInterceptor` whose emission point is `ClientHttpResponse.close()`), `./legatium-webclient-logging/` the reactive twin (an `ExchangeFilterFunction` with two hand-written Reactor operators whose emission point is the body publisher's terminal signal). `./consumer-smoke/` checks the shaded jars as a consumer sees them; `./benchmarks/` holds JMH measurements of the buffer and the body-meter cache.

**Stack detected.** Spring Boot 4.1.1 on Spring Framework 7.0.9, Micrometer 1.17.1; both blocking (`RestClient`/`RestTemplate`) and reactive (`WebClient`, Reactor) client stacks; no coroutines; virtual threads neither configured nor assumed (the one `synchronized` block in production code guards a `WeakHashMap` lookup, never a blocking call); no persistence, messaging, scheduling or controllers - this is a library, whose entry points are the interceptor, the filter, two auto-configurations, three customizers and one `SmartInitializingSingleton` per twin. Optional dependencies: `spring-boot-restclient`/`spring-boot-webclient` (customizers), `io.micrometer:context-propagation` (ADR-0010 restoration).

**Test code in scope: yes.** The three modules carry 145, 147 and 139 declared test methods (by annotation: 137 `@Test` + 5 `@ParameterizedTest` + 3 `@FuzzTest`; 146 + 1 `@FuzzTest`; 139 `@Test`), plus 3 in `consumer-smoke`; the blocking contract's 6 methods run in five engine suites and the reactive contract's 5 in four, so 171 resp. 154 executions. Test-quality heuristics were applied to every non-trivial test (evidential value by mutation thought experiment against the production code, determinism, isolation, risk-path coverage, sham concurrency, resource lifecycle, convention deviations against `./CONTRIBUTING.md`). The test review was split by module across three parallel reviewers working from the same production-code reading; every finding they reported was re-verified by the author (the level-OFF tests of both twins, the shared registry and the recomputed method order of the Boot suite, the smoke test's awaiting appender, the measuring tests of the reactive twin, the breaking-counters helper), and one of their candidates was rejected after cross-checking the twins (section 5, "Rejected candidates").

**Procedure.** Phase 1 ranked every production and test file (section 4). Phase 2 read every production file completely, concentrating on the code that changed since the previous report - the cache's miss path `cacheBodyMeter`, the `NoopMeter` rule, the rewritten KDoc on lock order and lifetime - and re-read the twins' lifecycle for regressions; the miss path was traced into Micrometer's `getOrCreateMeter` (the `accept` deny returning `noopBuilder.apply(mappedId)` without storing, `MeterRegistry.java:718-720`), `remove` (the listener loop inside `synchronized (meterMapLock)`, `:840-857`), `clear` (a `remove` per key) and `close` (no listener), and into the `noop` hierarchy (`NoopCounter`/`NoopDistributionSummary extends NoopMeter`), all from the version the build resolves. Phase 3 checked each candidate against reachability, framework contracts, ADRs, the module guide and the existing tests; style and taste items were discarded unless a documented convention was violated.

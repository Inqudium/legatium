# Retry Probe: does Reactor Netty's connection retry run the request tee twice?

1. Identification of the codebase
   - **Repository:** `https://github.com/Inqudium/legatium.git`
   - **Commit hash (HEAD at probe time):** `d4fb2d33` (the merge of PR #25, which made the reactive tee count before it copies)
   - **Reference (branch):** `refs/heads/docs/reactor-netty-retry-probe`
2. Question
   - Reactor Netty retries a request once, below the filter, when a pooled connection turns out to be stale. If that retry re-subscribed the request body publisher, `CapturingClientHttpRequestDecorator`'s tee would run again: the request size sample would double and the logged request body would carry the body twice (up to the cap). Raised by the counter-path review of 2026-09-17 as "to verify".
3. Source reading (Reactor Netty 1.3.7, `reactor.netty.http.client.HttpClientConnect.HttpObserver.onUncaughtException`)
   - The retry is set (`ops.retrying = true`, DEBUG "the request will be retried") only when `!ops.hasSentHeaders()`. Once headers or body were sent, `handler.shouldRetry = false` and the connection observes WARN "the request cannot be retried as the headers/body were sent".
   - The tee runs when the body publisher emits inside `writeWith`. For a `bodyValue` body Reactor Netty's `send(Mono)` obtains the buffer and marks and writes headers and body in one step on the channel's event-loop thread; for a `Flux` body the headers are sent before the first chunk. In both cases the tee never runs before the headers are marked sent. The retry can therefore fire only before `writeWith` ran at all, and a retried attempt is the FIRST run of the tee.
   - The one window the source leaves open is a body publisher emitting on a thread other than the event loop while the event loop processes the connection's death between the tee and `markSentHeaderAndBody` - microseconds, and not the shape of Spring's encoders, which emit inside `writeWith` on the event-loop thread.
4. Method
   - A raw HTTP/1.1 keep-alive peer on a `ServerSocket` (loopback, ephemeral port), each connection served on its own thread with a 3 s read timeout. A `WebClient` over `ReactorClientHttpConnector(HttpClient.create().responseTimeout(3 s))` with the filter (`logRequestBody = ALWAYS`, `measureRequestBodySize = true`) and a fresh `SimpleMeterRegistry` per run. Two `POST /upload` calls of `"hello"` (`bodyValue`, `Content-Length: 5`) per run; the peer answers the first with `200`, `Content-Length: 2`, `Connection: keep-alive`. `reactor.netty.http.client.HttpClientConnect` captured at DEBUG for the retry decision.
   - Observed per run: the peer's record of what arrived on which connection, the second call's outcome, Reactor Netty's retry-related log lines, the `adapter.request.body.size` summary and the `adapter_request_body` field of both events.
   - The probe class (`ReactorNettyRetryProbeTest`, three scenarios, prints, no assertions) was run once and not committed: it rests on sleeps and answers a question rather than pinning a contract.
5. Results

| Scenario | The peer | Second call | Reactor Netty's decision | Request size sample | Logged bodies |
|---|---|---|---|---|---|
| A (3 runs): the client waits 50 ms so the pooled connection is reused; the peer reads the second request in full and closes without answering | `conn1: hello`, `conn1-cut: hello` | `PrematureCloseException` | WARN "The connection observed an error" - the generic branch, no retry | 2 samples, 10 bytes: **5 per call, once** | `hello`, `hello` |
| B (3 runs): the peer closes the idle connection right after the first answer; the client waits 300 ms | `conn1: hello`, `conn2+: hello` | `200 ok` on a fresh connection | none - the pool had seen the FIN and evicted the connection | 2 samples, 10 bytes | `hello`, `hello` |
| D (5 runs): the client acquires the pooled connection after 30 ms, the peer closes it 60 ms after its answer, the body is a `Mono` that emits after 200 ms | `conn1: hello` | `AbortedException` | WARN "cannot be retried as the headers/body were sent" | 1 sample, 5 bytes (the second call's capture saw no byte) | `hello`, absent |

6. Verdict
   - **No double counting.** In no reachable scenario did Reactor Netty retry, and the source shows why the tee and the retry cannot overlap: the retry requires unsent headers, the tee runs no earlier than the headers are sent. Scenario D is the telling one - even a body that has not emitted when the connection dies is refused the retry, because Spring already sent the headers.
   - A pooled connection that dies after the request went out is one exchange line, `failure`, with the request body counted and logged once. A retry by `retryWhen` or an outer filter re-subscribes the whole exchange and is a separate attempt with its own line (module guide §4.7).
   - Documented in the module guide §4.7 and in the KDoc of `CapturingClientHttpRequestDecorator`. No code change.

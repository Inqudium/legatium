## 1. Executive summary

In the style sense this codebase is mature and, twelve days after the last style analysis, cleaner than it was then: every one of the twelve earlier findings is verified as fixed at this commit, and the checks that were red then are green now - 340 of 340 tests carry the CONTRIBUTING rationale block, no `!!` exists anywhere (production or tests), no `assertThatThrownBy` beside the 86 `catchThrowable`s, no production function exceeds 52 lines, and `ktlint` passes. The language is used the way it is meant to be: `fun interface` seams with `@JvmField`/`@JvmStatic` defaults for Java callers, `require`/`check` for invariants, `when` expressions, `object` for constants, closed sets as enums with a `tagValue`, extension functions for the builder overloads, string templates throughout, `internal` on 42 of 55 top-level declarations, no wildcard imports, no TODO debt, no non-English text, no commented-out code. Spring is used idiomatically: constructor-only wiring, one validated `@ConfigurationProperties` data class, `@ConditionalOnMissingBean` seams, the meter registry consumed through an `ObjectProvider`, no field injection outside Spring's own integration-test idiom. The degree of "Java in Kotlin" is close to zero.

The one High item is not in the code but between the code and its documentation tooling: the test-evidence generator cuts the rationale block at a stage label **with a colon**, while two thirds of the stage lines - and the example in CONTRIBUTING itself - carry none, so 217 of the 337 published "Why does it matter?" answers currently end in a stray `Given` or `Given/When/Then`. Below that, what remains is polish and, above all, **twin drift below the contract line**: the two entry points and emitters are deliberate copies (ADR-0003 keeps files under 90 % similarity as copies), and in the details the contract tests do not pin they have started to differ - the order in which the request-id origin is counted (one twin documents its order as deliberate, the other does the opposite), the content of the "abandoned" breadcrumb, the names of the completion functions, the visibility of the metrics owner, and a KDoc claim in the blocking twin about a breadcrumb the reactive twin does not write. The one Spring-idiom item is the pre-3.5 spelling of the boolean `enabled` condition on both auto-configurations. The Kotlin-idiom items are small and concrete: a `Pair` where the call site reads `.first`/`.second`, a manual superclass walk, three spellings of the same no-op `AutoCloseable`, a `return` inside a `try`-expression initializer, member ordering in the metrics owner.

On the test side the documented convention is followed almost perfectly (three truth-table tests lack the stage line), and the findings are about the house pattern rather than the rule: a dozen tests whose stage comments do not match their phases, helpers copied between the test classes of one module although each module has a `TestSupport.kt` for exactly that, the same Spring fixture written three times per twin, captured `var`s where a named recording fake would give a `val`, and some thirty fully qualified names inline where everything else is imported. The house style has a recognisable and consistently applied voice - dense constraint comments with capitalised emphasis words, `should …` backtick test names (340 of 340), AssertJ only, hand-written fakes only - and consistency, not doctrine, is the yardstick that produced most of the findings below.

## 2. Baseline & methodology

**Enforced rules (authority 1).**
- `ktlint` via ktlint-maven-plugin 3.7.1, `ktlint_official` code style, `ktlint:check` bound to `verify`; green at this commit. Formatting, import ordering, trailing commas, chained-call and argument wrapping (where the rules demand it), blank lines and indentation are tool-owned and not reported by hand.
- `./.editorconfig`: UTF-8, LF, final newline, 4-space indentation for Kotlin and XML/YAML/JSON, **`max_line_length = off`** - line length is deliberately unconstrained, so a long line is never a finding on its own; it appears below only where the *house pattern* of wrapping is broken (systemic pattern P1).
- No detekt, no ArchUnit, no Sonar, no IntelliJ inspection profile, no Java formatter in the repository. Their absence is noted as a known blind spot; the manual read covers what detekt would (complexity, naming, magic numbers, member ordering).

**Documented conventions (authority 2).**
- `./CONTRIBUTING.md`, "Code style": build from the root (friend paths, ADR-0003); ktlint; "match the surrounding code's comment density and naming; comments should state constraints the code can't express, not narrate the code".
- `./CONTRIBUTING.md`, "Tests": test classes `*Test.kt`; the three-line rationale block (`What is tested:` / `Success criteria:` / `Why it matters:`) at the top of every test body, **followed by the `Given/When/Then` stage comments - "a single `// Given/When/Then` line" for a truth-table test** (quoted without a colon); the Java fuzz targets carry the same block; fuzz targets in Java, not Kotlin (Scorecard); the test-evidence page is generated from these comments ("Your test's rationale comment is what appears there"); KDoc `[Symbol]` links are checked by Dokka `failOnWarning`.
- `./docs/adr/ADR-0007`: the operator-facing vocabulary is `adapter`, code names keep their `Client*` form - `ClientRequestLoggingInterceptor` beside `adapter_*` fields is a decided convention, not a naming finding.
- `./docs/adr/ADR-0003`: byte-identical twin code lives in `legatium-common` (90 % line-similarity rule per file); below the line a copy stays a copy. The ADR's history (2026-09-04) also decides that **test helpers are copied per twin** ("copies are cheaper than a test-jar" for helpers a module actually uses), so `CapturedLogger` in three places, `Tarpit.kt` byte-identical in both twins (verified by `diff` after neutralising the stack names) and the near-identical `PeerServer.kt`/`TestSupport.kt` are a documented decision, not a finding. Duplication *within* one module's test classes is not covered by that decision and is reported (finding 8).
- No English-only rule is written down; the codebase is English throughout, so no deviation exists to report.

**Stack.** Kotlin 2.4.20 (data classes, `fun interface`, `buildMap`, `HexFormat`, `ArrayDeque`, `entries` - all used), Java 21 in the fuzz targets and the smoke test, Spring Boot 4.1.1 (`@ConditionalOnBooleanProperty` available since Boot 3.5 - verified present in the resolved `spring-boot-autoconfigure-4.1.1.jar`), JUnit 6.1.3 BOM, the `spring` all-open plugin.

**De-facto house style (authority 3), derived from the majority of the code:**
- Visibility: `internal` by default (42 of 55 top-level declarations; 12 public: the properties classes, the three seams, `MdcKeys`, `BodyLogMode`, `BodyReadState`, the two entry points, the two auto-configurations; 1 private). Members that exist for the tests are marked `internal` with a KDoc saying so.
- Bodies: expression bodies where the body is one expression (69 by grep), block bodies otherwise (110) - consistent with the Kotlin Coding Conventions, no finding.
- Closed sets: `enum class` with a `tagValue` where a value goes on the wire (`BodyReadState`, `ClientOutcome`, `FailOpenStage`, `RequestIdSource`), `enum class` with behaviour (`BodyLogMode`), a typed enum for the field family (`ClientLogField`); seven of eight enums are laid out one entry per line.
- Immutability: `val` everywhere; every production `var` (23 via grep) is `@Volatile` lifecycle state on an `Exchange`/capture, lock-guarded capture state, a test seam (`internal var … Restorer`), or a loop/accumulator local. No `lateinit` outside the two Reactor subscribers' `upstream`.
- Fail-open shape: `reportQuietly { metrics.xFailure(); internalLog.warn(…) }` with the message, method, target and `e.toString()` as separate wrapped arguments (19 wrapped multi-argument log calls versus 2 single-line ones).
- Absent values: `null` for absent optional fields, `*IfPresent` builder extensions, `?.let`/`?:` chains; no `Optional` in Kotlin.
- Comments: dense KDoc stating constraints, capitalised emphasis words as a house idiom; consistent, therefore not a finding.
- Tests: JUnit 5, AssertJ only (no JUnit `Assertions`, no Hamcrest, no mock library - verified by grep), backtick names that are full `should …` sentences (340 of 340), rationale block (340 of 340), a stage comment (337 of 340), `catchThrowable` for exceptions (86 of 86), `@Nested` in the eleven larger classes, `@SpringBootTest` + `@Autowired lateinit var` only in the seven Spring integration tests (Spring's own idiom; `ApplicationContextRunner` where a runner suffices), injected time (`AtomicLong`-driven `NanoTimeSource`) and fixed ids throughout, `.block()` dominant (58) with `StepVerifier` (12) for signal-level facts, Java tests in `snake_case` (`should_…`, `parser_upholds_its_contract`). Stage labels: bare `// Given` in 557 lines, `// Given: …` with a colon in 231, spaced `// Given / When` in 14.

**Prior findings (re-verified at this commit).** All twelve findings of `CODE_STYLE-2026-09-04T22-19-30.md` are confirmed fixed: rationale blocks 340/340; `@JvmField` on `HeaderValueMasker.DEFAULT`, `NanoTimeSource.SYSTEM`, `CorrelationIdGenerator.DEFAULT` and `@JvmStatic` on `keyed`/`forKey`; the three vocabularies are enums (`ClientOutcome`, `FailOpenStage`, `RequestIdSource`); both `BoundedBodyCapture`s are `internal`; `toULong().toString(36)` and `kotlin.math.ceil`; the longest production function is now 52 lines (`wireExchange`, RestClient twin); both emitters classify through one `classify` returning the shared `Classification`; the `val outgoing = ….let{}.let{}` rebuild; zero `!!`; zero `assertThatThrownBy`; `FingerprintHeaderValueMasker` top-level; the fuzz target's predicate computed once. None of them is repeated below.

**Analyzed vs. not analyzed.** All production Kotlin and all test code of the three modules, plus the consumer smoke project; not analyzed: documentation prose, workflow YAML, the Python docs scripts (except the one regex finding 1 rests on), the ELK template JSON.

**Blind spots.** No inspection profile or complexity tool was run; complexity is judged by function length (awk over `fun … {` blocks) and nesting on reading. Test-side findings come from three module-scoped review passes; each was re-verified at the stated line, but a test-style deviation the passes did not surface would not appear here.

### 🟠 High

- [x] 1. [`./.github/scripts/generate-test-catalog.py:51` versus the stage comments of the whole test suite, e.g. `./legatium-common/src/test/kotlin/eu/inqudium/legatium/common/ClientActivationTest.kt:27`, `./legatium-restclient-logging/src/test/kotlin/eu/inqudium/legatium/restclient/logging/ClientRequestLoggingInterceptorTest.kt:221`, `./legatium-webclient-logging/src/test/kotlin/eu/inqudium/legatium/webclient/logging/ClientRequestLoggingFilterTest.kt:206`] {High} {Confidence: high} {Docs} The evidence generator and the documented stage-comment convention disagree on the colon, so two thirds of the published rationales end in a stray stage label
  - Actual pattern: the generator cuts the rationale run at `STAGES_RE = \b(?:Given|When|Then|And)\b\s*(?:\([^)]*\))?:` - the colon is mandatory. The test suite writes the stage label without a colon in 557 lines and with one in 231 (grep over `src/test/**/*.kt`, `^\s*// (Given|When|Then)(/…)*\s*$` versus `…\s*:`); CONTRIBUTING's own example is the colon-less `// Given/When/Then`. Executing the script's `extract_rationales` against the three modules at this commit: 217 of 337 rationale entries end with `Given`, `Given/When`, `Given/When/` or `Given/When/Then` in the "Why does it matter?" answer (e.g. `ClientActivationTest`, "…must log every call. Given/When/Then").
  - Reference: `./CONTRIBUTING.md` "Tests" - the rationale block followed by the stage comments, quoted as `// Given/When/Then`, and "Your test's rationale comment is what appears there - another reason to keep the pattern intact"; the script's own docstring ("cut off at the first Given/When/Then stage label").
  - Idiomatic alternative: decide the convention on one side. Either the generator accepts a stage label at the start of a comment line with an optional colon (the tests already follow CONTRIBUTING's spelling, so this is the smaller change), or CONTRIBUTING declares the colon form the rule and the 557 lines follow. The script is outside this report's style scope; the finding is the mismatch, which the test comments cannot resolve on their own.
  - Effect: correctness of the published test-evidence page (actively misleading text in 217 entries), and a convention that cannot currently be followed and rendered at the same time. Overlap: this is a tooling defect as much as a style item; noted, not explored further.

### 🟡 Medium

- [x] 2. [`./legatium-restclient-logging/src/main/kotlin/eu/inqudium/legatium/restclient/logging/ClientLoggingAutoConfiguration.kt:38`, `./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ClientLoggingAutoConfiguration.kt:39`] {Medium} {Confidence: high} {Spring idiom} The boolean `enabled` switch uses the pre-3.5 spelling of the property condition
  - Actual pattern: `@ConditionalOnProperty(prefix = "adapter-logging", name = ["enabled"], havingValue = "true", matchIfMissing = true)` on both auto-configurations.
  - Reference: Spring Boot ≥ 3.5 ships `@ConditionalOnBooleanProperty` for exactly this shape (present in the resolved `spring-boot-autoconfigure-4.1.1.jar`); Boot's own auto-configurations use it for boolean switches on 4.x.
  - Idiomatic alternative: the boolean condition annotation with `prefix`, `name` and `matchIfMissing`, dropping `havingValue`.
  - Effect: readability (the intent "on unless explicitly false" reads from the annotation name), consistency with the framework version the project targets.

- [x] 3. [`./legatium-common/src/main/kotlin/eu/inqudium/legatium/common/Traceparent.kt:31` and its consumer `./legatium-common/src/main/kotlin/eu/inqudium/legatium/common/ClientIdentity.kt:35,45-46`] {Medium} {Confidence: medium} {Kotlin idiom} A `Pair` stands in for a named trace context, and the call site reads `.first`/`.second`
  - Actual pattern: `parse(value): Pair<String, String>?`; `ClientIdentity.resolve` then writes `trace?.first` for the trace id and `trace?.second` for the span id - the reader must know the tuple order to know which id is which. (The two Java fuzz targets spell the same type as `kotlin.Pair<String, String>` five times, finding 44.)
  - Reference: Kotlin documentation on `Pair`/destructuring ("for readability, a named data class is often preferable"), Effective Kotlin item 37 ("Use the data modifier to represent a bundle of data" - explicitly against tuples for domain concepts); house pattern - every other named shape in the module is a class (`ClientIdentity`, `RequestTarget`, `Classification`).
  - Idiomatic alternative: a small `internal` value class or data class with `traceId` and `spanId`, returned by `parse` and read by name in `ClientIdentity`; the `Pair`s that carry header `(name, value)` lists and are destructured at their single use site are fine and not part of this finding.
  - Effect: readability at the one place the two ids are told apart; Java callers lose `getFirst()`.

- [x] 4. [`./legatium-restclient-logging/src/main/kotlin/eu/inqudium/legatium/restclient/logging/ClientRequestLoggingInterceptor.kt:55-58`] {Medium} {Confidence: high} {Docs} The interceptor's KDoc justifies the failure breadcrumb with a twin symmetry that does not exist
  - Actual pattern: "When the call throws, a short WARN breadcrumb is additionally logged on the module's OWN logger … the breadcrumb keeps the two twins' log streams alike". The reactive twin writes no breadcrumb for a failed call - its internal logger carries only the wiring error, the tee failure and the "abandoned" line (`grep -n 'exchange failed\|breadcrumb' ./legatium-webclient-logging/src/main` finds only the KDoc of `abandonExchange`).
  - Reference: `./CONTRIBUTING.md` "Code style" (comments state constraints, and must therefore be true); the twin-symmetry invariant of CONTRIBUTING "Project scope".
  - Idiomatic alternative: state the real reason for the breadcrumb (visibility of the cause at the moment of failure on the module's logger), or document the asymmetry as a stack difference in both KDocs - the reactive filter's KDoc already lists its deliberate differences and could carry this one.
  - Effect: a reader of the blocking twin expects a line the reactive twin never writes; actively misleading for whoever compares the two log streams. Overlap with the comment-audit domain; noted.

- [x] 5. [`./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ClientRequestLoggingFilter.kt:280-283` versus `./legatium-restclient-logging/src/main/kotlin/eu/inqudium/legatium/restclient/logging/ClientRequestLoggingInterceptor.kt:372-376`] {Medium} {Confidence: high} {Consistency} The twins count the request-id origin at opposite ends of the wiring, and only one of them says why
  - Actual pattern: the RestClient twin calls `metrics.requestId(identity.source)` as the LAST wiring step, right before `exchangeOpened()`, with a three-line comment explaining that a wiring failure above must leave the correlation sum equal to the number of exchanges actually opened. The WebClient twin calls it FIRST (line 282), before `newCaptures()`, the request rebuild and the header selection through the host masker - all of which can throw and take the `wireOrNull` path.
  - Reference: dominant house pattern for shared semantics (ADR-0003: "identical fields and configuration", `ClientIdentity.resolve` was extracted precisely so the ADR-0002 logic lives in one place); the RestClient twin's own documented rationale.
  - Idiomatic alternative: the same position and the same comment in the reactive twin, or - if the order is meant to differ - a comment there saying so. ## 6. Systemic patterns

Counting basis per pattern; representative locations only.

**P1 - Unwrapped long statements where the house pattern wraps (production, Low).** 34 lines longer than 140 characters in `src/main` (`awk 'length > 140'`; 72 in the tests) although the dominant fail-open log call wraps one argument per line (19 wrapped versus 2 single-line multi-argument `internalLog` calls). `max_line_length = off` is an explicit configuration decision, so no single line is a finding; the pattern is that the same statement shapes are wrapped in one place and not in another. Representative: `ClientRequestLoggingFilter.kt:289` (a 190-character `.let { if … else it }`), `AmbientContextRestorer.kt:43` (a 200-character `if`/`else` expression body), `ClientLoggingAutoConfiguration.kt:73,88,97` (RC) and `:67,82` (WC) (one-line bean methods with five parameters or a lambda), `newCaptures()` in both twins (finding 18), `abandonExchange` in both twins (findings 20/21). Strategy: either a `max_line_length` in `.editorconfig` (ktlint then wraps mechanically - a decision, since the project switched it off) or, keeping it off, wrapping by the dominant shape at these few sites.

**P2 - Twin drift below the contract line (production, Medium/Low).** The entry points and emitters are deliberate copies (ADR-0003), and the contract tests pin the operator-facing surface; everything below it has begun to diverge: the request-id count position (finding 5), the KDoc breadcrumb claim (finding 4), the breadcrumb content (finding 21), the completion-function names and metrics visibility (finding 20), the no-op scope spelling (finding 15). 5 instances, found by reading the twins side by side (`diff` after neutralising the stack names). Strategy: a twin review step - for each change to one twin, diff the other for the same hunk - and a KDoc "deliberate stack differences" list in the blocking twin like the one the reactive filter already has.

**P3 - Stage-label spelling variance (tests, High via finding 1).** Bare `// Given` in 557 lines, `// Given: …` in 231, spaced `// Given / When` in 14 (three files, finding 24), no label in 3 tests (finding 6); the evidence generator accepts only the colon form. Strategy: decide the spelling once (finding 1), then the 14 spaced lines and the 3 missing lines follow.

**P4 - Test-helper duplication inside one module (tests, Medium).** ~14 sites across the three modules (findings 8 and 9; counting basis: `grep -n 'fun ClientRequestLoggingFilter.call\|fun buffer(\|fun filterWith\|fun interceptorWith\|onAnotherThread\|object : TurboFilter\|object : SimpleMeterRegistry\|lateinit var peer\|var previousLevel'`). The ADR-0003 decision on copies covers copies between twins; within a module each twin already has `TestSupport.kt`. Strategy: move per-module helpers there and give the Spring fixture one owner per twin.

**P5 - Inline fully qualified names in the tests (tests, Medium).** ~34 sites (finding 11; 17 WC, 12 RC, 5 Java) against zero in production and in 13 of 20 WC test files. Strategy: imports.

**P6 - `lateinit var` in `@BeforeEach` for fixtures a `val` could hold (tests, Low).** 8 sites (finding 27; `grep -n 'lateinit var' src/test` minus the Spring `@Autowired` fields and the companion `peer`). Strategy: `val` initializers, keeping only the `@AfterEach` teardown.

**P7 - `Pair` as a domain tuple (production, Medium/Low).** 3 sites where the tuple stands for a named concept: `Traceparent.parse` (finding 3, read as `.first`/`.second`) and `loggedBodies` returning `Pair<String?, String?>` in both emitters (`ExchangeLogEmitter.kt:287` RC, `:304` WC - destructured at the single call site, so not reported individually). The 10 other `Pair` uses carry header `(name, value)` lists and are destructured where read; those are idiomatic. Strategy: a named type for the trace context; the bodies pair may stay.

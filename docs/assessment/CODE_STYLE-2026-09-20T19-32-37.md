## 1. Executive summary

Four days and 102 commits after the previous style analysis, the codebase is in the style sense as mature as it was then and cleaner in the places that report addressed: 41 of its 44 findings are verified as applied at this commit (the two declined items and the one partial are documented in its section 7 and are not repeated here), `ktlint` is green, every one of the 435 tests carries the CONTRIBUTING rationale block and a `should …` backtick name, no `!!`, no `assertThatThrownBy`, no mocking library, no wildcard import, no TODO, no commented-out code and no non-English text exists anywhere in the sources. The language is used the way it is meant to be - `fun interface` seams with `@JvmField`/`@JvmStatic` defaults, `require`/`check` for invariants, `when` expressions, `object` for constants, enums with a `tagValue` for every wire vocabulary, extension functions for the builder overloads, `internal` on 41 of 57 top-level declarations, a named `TraceContext` where a `Pair` used to be - and Spring is used idiomatically: constructor-only wiring, one validated `@ConfigurationProperties` data class, `@ConditionalOnBooleanProperty` on both switches, `@ConditionalOnMissingBean` seams, the meter registry consumed through an `ObjectProvider`. The degree of "Java in Kotlin" remains close to zero.

There is nothing Critical and nothing High. The seven Medium items are two production-side items - the startup wiring report names the correlation header by its default literal although the header is configurable, and the RestClient twin's caller-MDC restoration re-implements the best-effort restore loop that `MdcScope` already owns in the shared module - and five items on the test and benchmark side: the registry-counter lookup is written as four differently named private helpers plus some twenty inlined six-line chains across five classes, the Spring test application of the RestClient twin lives at the bottom of one suite's file while three suites boot it, three truth-table tests run the subject under the `// Given` label, two rationale sentences describe a case their test does not run, and the write benchmark's `chunk` parameter has a second value the code never uses. Everything else is polish: class-layout order slipped again where the body-meter cache was added, one camelCase constant among eleven SCREAMING ones, the two private seams without an explicit type, the `internal` test-seam marker applied to some exposed members and not others, small within-module duplications in the test suites, and a handful of stage-comment placements.

The premise the previous report's High finding rested on has been resolved on the generator side: the evidence generator now accepts the bare stage label CONTRIBUTING prescribes as well as the qualified `Label: text` form, so the 746 bare and 332 qualified labels are both conformant and no colon-related item appears below. One house pattern has become genuinely two-sided since then - fakes throw with `error(…)` in nine places and with `throw IllegalStateException(…)` in fifteen - and is reported once as a pattern rather than per site.

## 2. Baseline & methodology

**Enforced rules (authority 1).**
- `ktlint` via ktlint-maven-plugin 3.7.1, `ktlint_official` code style, `ktlint:check` bound to `verify`; green at this commit. Formatting, import ordering, trailing commas, chained-call and argument wrapping (where the rules demand it), blank lines and indentation are tool-owned and not reported by hand.
- `./.editorconfig`: UTF-8, LF, final newline, 4-space indentation for Kotlin and XML/YAML/JSON, **`max_line_length = off`** - line length is deliberately unconstrained (confirmed as a decision in the previous report's section 7), so a long line is never a finding on its own. No indentation rule is declared for `*.java`; the Java files use 4/8 spaces uniformly.
- No detekt, no ArchUnit, no Sonar, no IntelliJ inspection profile, no Java formatter (the three Java projects - fuzz targets, smoke test, benchmarks - are formatted by hand). Their absence is noted as a known blind spot; the manual read covers what detekt would (complexity, naming, magic numbers, member ordering), and the Java side is judged only on clear intra-file inconsistencies (systemic pattern P8).

**Documented conventions (authority 2).**
- `./CONTRIBUTING.md`, "Code style": build from the root (friend paths, ADR-0003); ktlint; "match the surrounding code's comment density and naming; comments should state constraints the code can't express, not narrate the code".
- `./CONTRIBUTING.md`, "Tests": test classes `*Test.kt`; the three-line rationale block (`What is tested:` / `Success criteria:` / `Why it matters:`) at the top of every test body, followed by the `Given/When/Then` stage comments (a single `// Given/When/Then` line for a truth-table test); the Java fuzz targets carry the same block; fuzz targets in Java, not Kotlin (Scorecard); the test-evidence page is generated from these comments; KDoc `[Symbol]` links are checked by Dokka `failOnWarning` and therefore **a `[Symbol]` in a `//` line comment is to be avoided** ("name the symbol in backticks there"); integration tests against a real engine pin the module's classification, not the engine's exception type or message (decision of 2026-09-19).
- **Stage labels:** `./.github/scripts/generate-test-catalog.py:49-58` (`STAGE_LINE_RE`) accepts a stage line with or without a `: text` qualifier and with or without spaces around the slashes, and states "CONTRIBUTING's spelling is the bare label, the colon form is equally common in the suites". The bare label is therefore the documented form, the qualified form an accepted variant; neither is a finding. Only labels outside the vocabulary (`And when`) and the spaced `Given / When / Then` variant - accepted by the generator, but a third spelling against 746 + 332 of the other two - are reported (finding 27).
- `./docs/adr/ADR-0007`: the operator-facing vocabulary is `adapter`, code names keep their `Client*` form - `ClientRequestLoggingInterceptor` beside `adapter_*` fields is a decided convention, not a naming finding.
- `./docs/adr/ADR-0003`: byte-identical twin code lives in `legatium-common` ("a twin-paired file that reaches 90 % line similarity after neutralising the stack names is byte-identical enough to move … Below that, a copy stays a copy"); the emitters (72 %), the exchanges and the two `BoundedBodyCapture`s remain duplicated by decision, and test helpers are copied per twin ("copies are cheaper than a test-jar"). So `Tarpit.kt`, `PeerServer.kt`, `TestSupport.kt`, the `CapturedLogger` copies and the two `Captures` holders are not findings; duplication *within* one module is (findings 4, 23-26), and so is drift *below* the contract line where the copies have no documented reason to differ (P1).
- No English-only rule is written down; the codebase is English throughout (the six non-ASCII hits are the `aä€😀` test data).

**Stack.** Kotlin 2.4.20 (data classes, `fun interface`, `buildMap`/`buildList`, `HexFormat`, `ArrayDeque`, `entries`, `generateSequence` - all used), Java 21 in the fuzz targets, the smoke test and the JMH benchmarks (records not needed there, arrow switches and streams in use), Spring Boot 4.1.1 (`@ConditionalOnBooleanProperty` in use on both auto-configurations), JUnit 6.1.3, JMH 1.37, the `spring` all-open plugin.

**De-facto house style (authority 3), derived from the majority of the code (counting basis: grep over `src/main/**/*.kt` unless stated):**
- Visibility: `internal` by default (41 of 57 top-level declarations; the public ones are the properties classes, the three seams, `MdcKeys`, `BodyLogMode`, `BodyReadState`, the two entry points, the two auto-configurations; 1 private). Members that exist for the tests carry an `internal` modifier plus a KDoc saying so ("exposed for the tests") - 12 such members; finding 15 is where the marker is missing on a member with the same KDoc.
- Bodies: expression bodies where the body is one expression (61), block bodies otherwise (71) - consistent with the Kotlin Coding Conventions; finding 16 is the one within-file exception.
- Closed sets: `enum class` with a `tagValue` where a value goes on the wire (`BodyReadState`, `ClientOutcome`, `FailOpenStage`, `RequestIdSource`, `ClientStack`), `enum class` with behaviour (`BodyLogMode`), a typed enum for the field family (`ClientLogField`); all eight enums laid out one entry per line.
- Constants in objects and companions: SCREAMING_SNAKE for `const val` and for deeply immutable `val`s (`Regex`, `Set`, `Map`, `ConfigurationPropertyName`, `HexFormat` - 11 of 12); finding 9 is the twelfth.
- Immutability: `val` everywhere; every production `var` (28) is `@Volatile` lifecycle state on an `Exchange`/capture, lock-guarded capture state, a documented test seam (`internal var … Restorer`), or a loop/accumulator local. No `lateinit` outside the two Reactor subscribers' `upstream`. No `!!`.
- Fail-open shape: `reportQuietly { metrics.xFailure(); internalLog.warn(…) }` with message, method, target and `e.toString()` as separately wrapped arguments (21 wrapped multi-argument calls versus 2 six-argument single-line ones, finding 14). The module's own logger is `internalLog` in the five classes that also emit on another logger's behalf and `log` in the two auto-configurations (finding 12).
- Seams: `fun interface` with a companion `@JvmField val DEFAULT/SYSTEM: <Type>` carrying an explicit type (4 of 6; finding 10).
- Class layout: properties and `init` first, then functions, then the companion - followed by 35 of the 40 production classes; the companion holds constants before functions in every companion but one (finding 8).
- Absent values: `null` for absent optional fields, `*IfPresent` builder extensions, `?.let`/`?:` chains; `Pair` only for header `(name, value)` lists and the two `loggedBodies` tuples destructured at their single call site (P7).
- Comments: dense KDoc stating constraints, capitalised emphasis words as a house idiom; consistent, therefore not a finding. KDoc `[Symbol]` links in KDoc only - three `//` comments carry one (finding 19).
- Tests: JUnit 5/6, AssertJ only (no JUnit `Assertions`, no Hamcrest, no mock library - verified by grep), backtick names that are full `should …` sentences (431 of 431 Kotlin tests; the four Java fuzz targets use `snake_case`), rationale block (435 of 435), a stage comment on every Kotlin test (the four Java fuzz targets carry the rationale block only - consistent among themselves and not required by CONTRIBUTING, which names the block), `catchThrowable` for exceptions (114 of 114), `@Nested` (55) in the larger classes, `@SpringBootTest` (10) + `@Autowired lateinit var` (9) only in the Spring integration suites (Spring's own idiom; `ApplicationContextRunner` where a runner suffices), injected time (`AtomicLong`-driven `NanoTimeSource`) and fixed ids throughout, `.block()` dominant (52) with `StepVerifier` (12) for signal-level facts, a shared `IntegrationFixture` + `PeerExtension` in the WebClient twin and a `PeerIntegrationSuite` in the RestClient twin, zero inline fully qualified names in code, `requireNotNull` instead of `!!`, precondition asserts under `// Given`. Fakes are named classes recording into `val` properties (`RecordingExchange`, `CapturedLogger`, `PeerServer.received`), with ~9 captured-`var` exceptions (finding 22); they throw with `error(…)` in 9 sites and `throw IllegalStateException(…)` in 15 (P3, finding 20) - the one house pattern that is no longer one-sided.

**Prior findings (re-verified at this commit).** Of the 44 findings of `CODE_STYLE-2026-09-16T21-47-00.md`, the 41 its section 7 lists as applied are confirmed at this commit by direct inspection: the generator accepts both stage-label forms (1); `@ConditionalOnBooleanProperty` on both auto-configurations (2); `TraceContext` data class read by name in `ClientIdentity` (3); the interceptor KDoc names the breadcrumb a deliberate stack difference and the filter KDoc lists it (4); both twins count the request-id origin LAST with the same comment (5); the three truth-table tests carry `// Given/When/Then` (6); the `NoOpScope` object (15); `generateSequence` in `Timeouts` (16); `ClientStack.tagValue` (12); one-entry-per-line `ExchangeState` (22); streams in the smoke test (23); the abandoned breadcrumb carries the request id in both twins (21); the completion functions and `internal val emitter` are aligned (20); the WebClient `IntegrationFixture`/`PeerExtension` and the RestClient `PeerIntegrationSuite` replaced the three-times-written fixture (9); `RecordingExchange` and `filtersOf`/`interceptorsOf` (10); no inline FQNs (11); `Received` is a data class (37); no `assertThat` in a `by lazy` (42); the fuzz targets' imports are sorted (44); and so on. ### 🟡 Medium

- [x] 1. [`./legatium-common/src/main/kotlin/eu/inqudium/legatium/common/ClientObservationWiring.kt:775,783`] {Medium} {Confidence: high} {Docs} The wiring report names the correlation header by its default literal although the header is a property
  - Actual pattern: the two "no observation" / "observed, not traced" lines end in "the module generates the request id and sends X-Correlation-Id on every call that carries no traceparent" - the literal `X-Correlation-Id` is written into the message text, while the header actually sent is `ClientLoggingProperties.correlationIdHeader` (default `X-Correlation-Id`, validated as an RFC 9110 token, i.e. meant to be changed). `describe(beanFactory, customizers, tracerClass)` has no access to the properties, so the report cannot say the configured name.
  - Reference: `./CONTRIBUTING.md` "Code style" (comments and messages state constraints, and must therefore be true); house pattern - every other place that addresses the configured header goes through `properties.correlationIdHeader` (both entry points, both test suites, which the previous report's finding 32 aligned).
  - Idiomatic alternative: hand the configured header name (or the properties) into `describe` from the two auto-configurations, which already have the properties bean, and render it in the two messages; or drop the header name from the sentence ("sends the configured correlation header").
  - Effect: correctness of the DEBUG wiring report for a host that configured another header - the one report meant to explain the identity contract then names a header the host never sees; overlap with the defect and comment-audit domains, noted.

- [x] 2.   - Actual pattern: `CallerMdcSnapshot.restorePrevious(previous)` and `MdcScope.close()` are the same twelve lines - `var failure: Exception? = null`, the `forEach { (key, value) -> try { if (value == null) MDC.remove(key) else MDC.put(key, value) } catch … }`, the `first == null` / `addSuppressed` merge, `failure?.let { throw it }` - and the partial-install rollback in `restore()` (lines 42-50) mirrors `MdcScope`'s `init` rollback (`Mdc.kt:83-92`) with the comment "as MdcScope does".

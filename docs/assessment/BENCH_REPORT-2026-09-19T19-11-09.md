## 1. Executive summary

One body-size sample through the metrics owner cost **83-85 ns and 448 B** before this change and costs **35-36 ns and 32 B** after it; the floor - `DistributionSummary.record` on a summary already in hand - is **28 ns and 0 B**. The change removes 93 % of the allocation and 58 % of the time of the step, and leaves the owner 7 ns and one 32-byte key above what the meter itself costs. The figures are the same with one tag set and with sixteen rotating ones, so the gain is not a single hot entry.

What the numbers say about the old decision: "Micrometer's registry is the deduplicating cache" was true and is still true - the registry finds the existing meter on one `ConcurrentHashMap` lookup - but the lookup needs a `Meter.Id` to look up, and building that id from a builder and three tags is what the 448 B and the extra 50 ns were. The registry deduplicates *meters*; it cannot deduplicate the *work of asking for one*. A measured exchange asks three times (request size, response size, response read state), so the change saves about 1.3 KB and 150 ns per measured exchange on the opt-in path. Relative to the emission that follows - a formatted line of a few hundred bytes plus its MDC scopes - that is a small share; it is nonetheless the largest avoidable allocation on that path, and it went away for the cost of a map and a removal listener.

**Verdict - accepted.** Finding 20 is closed with this measurement; pattern P1 with it. The two correctness cases the cache introduces (a host removing a meter, a host rejecting a meter's id) are not measured here but pinned by tests (section 4.5). The cache holds one entry per body meter the registry holds - at most 5 · (T + 1) · H · N per owner for T templates, H peers and N named clients, about 70 B each against several hundred bytes per meter - and has no bound of its own because the bound is the registry's (section 5).

## 2. The two variants, and the floor

Everything measured lives in `eu.inqudium.legatium.common.ClientLoggingMetrics`, the metrics owner both twins inline (ADR-0003). The method under measurement is `requestBodySize`, which delegates to the private `recordBodySize`; `responseBodySize` is the same method with another meter name, `responseBodyRead` the same shape on a `Counter`. The benchmark measures the summary path; the counter path differs only in the meter type.

### 2.1 Variant A - register per call (the owner before this branch)

This is the code as it stood after the fix round of 2026-09-19 (with the `updateQuietly` guard of finding 6; before that round the body was the same without the guard):

```kotlin
private fun recordBodySize(
    meterName: String,
    template: String?,
    host: String?,
    name: String?,
    bytes: Long,
) {
    if (bytes == 0L) {
        return
    }
    updateQuietly(meterName) {
        registerOrFallback(meterName) { registry ->
            DistributionSummary
                .builder(meterName)
                .baseUnit("bytes")
                .description("Bytes of the body that actually flowed through the exchange")
                .tag("uri", uriTag(template))
                .tag("host", host ?: UNKNOWN_HOST)
                .tag("name", name ?: UNNAMED_ADAPTER)
                .register(registry)
        }.record(bytes.toDouble())
    }
}
```

Every call runs the whole chain: a `DistributionSummary.Builder` is created, three `.tag()` calls each merge one more tag into a fresh sorted `Tags` instance (Micrometer's `Tags` is immutable; `tags.and(key, value)` copies and sorts), `register` builds a `Meter.Id` from name, tags, unit and description plus a `DistributionStatisticConfig` from the builder's config builder, and hands both to the registry. The registry (section 2.3) finds the summary it already holds and returns it; `record` then adds the sample. The `registerOrFallback` wrapper adds a try/catch around `register` and nothing on the happy path.

Nothing in this chain is wrong. Micrometer's own documentation shows exactly this shape for meters with dynamic tags, and the registry guarantees that the second call returns the meter the first one created. The question was only what the chain costs when it runs three times per exchange for the lifetime of a host.

The benchmark reproduces this variant as `registerPerCall`: the identical builder chain, inlined in the benchmark (the private method is not callable from outside the class), followed by `record`. It is byte-for-byte the id the owner built, so the registry hit is the same hit.

### 2.2 Variant B - resolve once per tag set, cache the meter (the owner on this branch)

```kotlin
/**
 * The tag set of one dynamic body meter, already folded the way the tags are ([uriTag], the host and
 * name fallbacks), so every raw input that yields the same meter id shares one entry.
 */
private data class BodyMeterKey(
    val meterName: String,
    val uriTemplate: String,
    val host: String,
    val name: String,
    val state: String? = null,
)

private val bodySizeSummaries = ConcurrentHashMap<BodyMeterKey, DistributionSummary>()
private val readStateCounters = ConcurrentHashMap<BodyMeterKey, Counter>()

init {
    // A host that removes one of the cached meters (`MeterRegistry.remove`) gets it registered anew
    // on the next exchange; without this the owner would keep recording into the detached instance.
    meterRegistry.config().onMeterRemoved { removed ->
        bodySizeSummaries.values.removeIf { it === removed }
        readStateCounters.values.removeIf { it === removed }
    }
}

private fun recordBodySize(
    meterName: String,
    template: String?,
    host: String?,
    name: String?,
    bytes: Long,
) {
    if (bytes == 0L) {
        return
    }
    updateQuietly(meterName) {
        val key = BodyMeterKey(meterName, uriTag(template), host ?: UNKNOWN_HOST, name ?: UNNAMED_ADAPTER)
        // The plain get first, as in responseBodyRead: the key is the hit path's only allocation.
        val summary =
            bodySizeSummaries[key] ?: bodySizeSummaries.computeIfAbsent(key) {
                registerOrFallback(meterName) { registry ->
                    DistributionSummary
                        .builder(meterName)
                        .baseUnit("bytes")
                        .description("Bytes of the body that actually flowed through the exchange")
                        .tag("uri", key.uriTemplate)
                        .tag("host", key.host)
                        .tag("name", key.name)
                        .register(registry)
                }
            }
        summary.record(bytes.toDouble())
    }
}
```

The builder chain is the same as in variant A - it now runs once per tag set, inside `computeIfAbsent`, on the first sample for that template, host and name. Every later sample builds the key (five references, 32 bytes), looks it up, and records. Three things about the shape are deliberate:

- **The key is built from the folded tag values, not the raw inputs.** `uriTag` folds a template without a placeholder to `UNTEMPLATED`, a null host to `UNKNOWN`, a null name to `UNNAMED` - the same folding the tags get. Two raw inputs that yield the same meter id therefore share one entry, and the cache holds exactly one entry per meter the registry holds under these names. That is why it needs no size policy of its own: its cardinality *is* the registry's, bounded by the same rules (the `uri` folding, the documented precondition that the host tag is low-cardinality). Section 5 derives the expected number of entries.
- **The plain `get` comes before `computeIfAbsent`.** `computeIfAbsent` takes a lambda, and a lambda that captures state is an object; Kotlin allocates it at the call, hit or miss. On the hit path - every sample but the first per tag set - the `get` finds the entry and the lambda is never built. The first run of the benchmark, without the `get`, measured 72 B/op; with it, 32 B - the key alone.
- **The removal listener closes the one way cache and registry can drift apart.** `MeterRegistry.remove` is the only operation that makes a cached reference stale; a host that calls it (rare, but part of the API) would otherwise have the owner recording into a meter no exporter reads. The listener drops the entry, and the next sample registers anew.

The benchmark measures this variant as `owner`: the production method `metrics.requestBodySize(...)`, on an owner whose cache was warmed for every tag set in setup - the steady state a long-running host sees.

### 2.3 What Micrometer does on `register` - why "the registry deduplicates" was right and yet costs

`DistributionSummary.Builder.register(registry)` (Micrometer 1.17.1) is:

```java
public DistributionSummary register(MeterRegistry registry) {
    return registry.summary(new Meter.Id(name, tags, baseUnit, description, Type.DISTRIBUTION_SUMMARY),
            distributionConfigBuilder.build(), scale);
}
```

and `MeterRegistry.summary` goes through `registerMeterIfNecessary` into `getOrCreateMeter`, whose first lines are:

```java
Meter m = preFilterIdToMeterMap.get(originalId);
if (m != null && !isStaleId(originalId)) {
    checkAndWarnAboutDoubleRegistration(m);
    return m;
}
Meter.Id mappedId = mapId(originalId);
m = meterMap.get(mappedId);
...
```

So on a repeat registration the registry does one `ConcurrentHashMap` lookup keyed by the *original* id, before any `MeterFilter` runs, and returns the existing meter. That is the deduplication the three earlier reports relied on, and it is cheap: hashing a `Meter.Id` (name plus three tags) and one map read. What it cannot avoid is everything that happens *before* the lookup in the caller - the builder, the three `Tags` merges, the `Meter.Id` and the `DistributionStatisticConfig` that `register` builds so it has something to look up with. The 448 B of variant A are those objects; the 32 B of variant B are the one key object the owner's own lookup needs instead.

(A subtlety worth recording: older Micrometer versions ran the filter chain's `map` on every registration before the lookup; since the pre-filter map exists, they do not. A benchmark on such a version would show a larger gap in time. The allocation gap is the same either way.)

### 2.4 The floor - `record` on a resolved summary

```java
resolved[slot()].record(BYTES);
```

`DistributionSummary.record` on a `SimpleMeterRegistry` summary: a `CumulativeDistributionSummary` updates a `LongAdder` count, a `DoubleAdder` total and a max. No allocation, about 28 ns on this machine. Nothing above it in either variant can go below this; the distance to it is what the variant costs.

### 2.5 What the benchmark does, and the two traps it avoids

`BodyMeterRecordBenchmark` is one `@State(Scope.Benchmark)` class with a `SimpleMeterRegistry`, the owner obtained through `ClientLoggingMetrics.forRegistry` exactly as a twin obtains it, and `tagSets` ∈ {1, 16} URI templates (`https://api.example.com/things/<i>/{id}`). Each operation records one 1 024-byte sample under the next template in rotation (a mask, since the counts are powers of two). Three benchmark methods: `owner` (variant B, the production method), `registerPerCall` (variant A, inlined) and `recordOnly` (the floor, on summaries resolved once in setup).

- **Rotation over tag sets.** With one tag set a cache benchmark measures one hot entry that stays in a register or an L1 line; sixteen rotating entries make the map do real hashing and reading. That both columns agree within 1-2 ns says the map read is not the cost.
- **Warmed cache.** Setup records one sample per template through the owner, so no measurement iteration sees a miss. The miss path is variant A plus a map insert, once per tag set per process lifetime; it is not what a host pays per exchange and it is not measured.
- **No blackhole games.** `record` mutates registry state, which is a side effect the JIT cannot eliminate, so the methods return `void`. The first buffer benchmark of this repository (`BENCH_REPORT-2026-09-17T17-07-53.md`, section 4 of its metadata block) was bitten by returning a scalar from a non-escaping object; here the object escapes into the registry by construction.

## 4. Findings

### 4.1 Allocation: 448 B down to 32 B per sample - Confirmed

Variant A allocates 448 B per sample with one tag set and 461 ± 15 B with sixteen (the 13 B difference is the longer template strings' share of the `Tags` copies, within the CI). Variant B allocates exactly 32 B: one `BodyMeterKey` - an object header of 12 B and five compressed references of 4 B, padded to 32 B. The floor allocates nothing. So of the 448 B, 416 B were the builder chain and the id, 32 B are what the owner's lookup keeps.

Per measured exchange (three samples): about 1 344 B before, 96 B after. At 1 000 measured exchanges per second that is 1.3 MB/s of short-lived garbage that no longer exists - a young-generation load, never a leak, but a load that scaled with the traffic on a path whose purpose is to be cheap enough to leave on.

### 4.2 Time: 84 ns down to 35 ns per sample, 7 ns above the floor - Confirmed

Variant A takes 83-85 ns, variant B 35-36 ns, the floor 28 ns. The 7 ns between B and the floor are the key's construction, its hash (five reference hashes combined by the data class) and the map read. The 49 ns between A and B are the builder chain and the id.

The absolute figures are JDK 26 on a turbo-enabled workstation; the ratio - variant B at 42 % of variant A's time - is the transferable number. On a target JDK 21 the builder chain would not be cheaper (it is allocation-bound), so the ratio is, if anything, conservative.

### 4.3 Independent of the number of tag sets - Confirmed

One versus sixteen rotating tag sets changes variant B by 1.2 ns and variant A by 1.9 ns, both within twice the CI. The cache's cost is not that of a hot single entry, and Micrometer's lookup is not helped by one either. A host with a few hundred templates would sit on the same numbers until the map exceeds a cache level, which at 32-byte keys and a few hundred entries it does not.

### 4.4 What the old decision got right, and what it missed - Assessed

The recorded decision was that Micrometer's registry already deduplicates and that a second cache would trade the builder, tags and filter-chain allocations for a tuple key, a size policy and cardinality bookkeeping. Two of its three premises hold: Micrometer deduplicates, and the second cache does need a key. The third does not: the cache needs no size policy and no bookkeeping, because - keyed on the folded tags - it holds one entry per meter the registry holds under the three names, and the registry's cardinality is already bounded by rules the owner enforces (`uriTag`) or documents (the host tag). The cache mirrors; it does not decide.

What the decision could not know without measuring was the size of the trade: a tuple key of 32 B against 448 B, 7 ns against 56 ns. The reports were right to ask for the benchmark rather than guess; the benchmark says the trade is worth taking.

### 4.5 The two correctness cases are tested, not measured - Recorded

A cache of meter references has exactly two ways to be wrong against a live registry, and neither shows in a throughput number:

- **A host removes a meter.** `MeterRegistry.remove` makes the cached reference stale; the owner would record into an instance no exporter reads. `ClientLoggingMetricsTest.should register a body meter anew after the host removed it instead of recording into the detached one` removes both a summary and a counter after a sample and asserts that the next sample lands in a *new* meter the registry holds (count 1, the new amount) while the removed instance saw nothing more.
- **A host rejects a meter's id.** Micrometer refuses a registration whose id exists with another type; the owner's `registerOrFallback` keeps such a meter in its private registry with one warning. Behind the cache this path runs once per tag set, and `should keep a body meter private with one warning when the host rejects its registration` pins that three samples against a host gauge under the summary's exact id neither throw nor reach the host, and warn once.

## 5. Expected cardinality of the cache

The cache has no bound of its own, so the question a reviewer must be able to answer is how many entries it holds in a real host and why that number cannot run away on its own. The answer follows from the key.

### 5.1 What the key is made of

Every entry is one `BodyMeterKey(meterName, uriTemplate, host, name, state)`, built from the FOLDED tag values - the same values the meter's `Meter.Id` carries. The five components have these sources and these bounds:

| Component | Source | Values | Bounded by |
|---|---|---|---|
| `meterName` | fixed | 2 in the summary map (`adapter.request.body.size`, `adapter.response.body.size`), 1 in the counter map | the code |
| `uriTemplate` (the `uri` tag) | the URI template the client recorded for the request (`RestClient`/`WebClient` set the template attribute for `.uri("/things/{id}", 7)`; an expanded `URI` or a template without a placeholder carries none), folded by `uriTag`: a template with a `{placeholder}` is kept, everything else becomes `UNKNOWN` | T + 1, where T is the number of distinct placeholder-bearing templates the client's code uses | the call sites in the application's code - a template is a string literal at a call site, not a value from traffic; a client that never uses templates has T = 0 |
| `host` | `RequestTarget.host`, the peer's authority with an explicit port (`api.example.com`, `127.0.0.1:44169`); `UNKNOWN` without one | H, the number of distinct peers the client is used against | the application's configuration for a client with a base URL (H = 1); the documented precondition of the opt-in measuring properties otherwise - a host built from caller data (a webhook URL, a tenant-specific authority) buys the cardinality it asks for, on the registry first |
| `name` | the client's name, a request attribute the host sets once per client builder (ADR-0009); `UNNAMED` without one | N, the number of named clients of one application on one registry | the host's vocabulary - one constant per client builder, "not folded or validated" by design (common guide §7.7) |
| `state` | `BodyReadState`, counter map only | 3 (`unread`, `partial`, `complete`) | the code |

The components are the meter's tags. That is the whole argument in one sentence: the cache cannot hold an entry the registry does not hold a meter for, because both are keyed on the same folded values, and it cannot hold two entries for one meter, because the folding happens before the key is built.

### 5.2 The bound, and what a host actually sees

Per owner - one per registry and stack, so a host carrying both twins has two, each with its own clients:

- summary map: at most 2 · (T + 1) · H · N entries,
- counter map: at most 3 · (T + 1) · H · N entries,
- together at most **5 · (T + 1) · H · N**.

The bound is loose in practice, in the registry's favour and the cache's alike:

- A size summary exists only for a tag set that saw a body of more than zero bytes in that direction (the zero-byte rule of `recordBodySize`). The request-side summary of a GET route never exists; the response-side summary of a `204` route neither.
- A read-state counter exists only for a state that occurred: a route whose body is always read to the end has one counter, not three.
- The summaries exist only with `measure-request-body-size` resp. `measure-response-body-size` on; the counter with the latter. All three are opt-in and off by default - a host that does not measure has an empty cache.

Worked examples, all per owner (a host carrying both twins has two owners and counts each twin's clients on its own). 

- T is the number of placeholder-bearing templates PER client, 
- H the peers per client, 
- N the named clients;

The bound is `N · 5 · (T + 1) · H`. 

The "typical" column applies the three rules above with one assumption each: half the routes send a body (request summary on half the tag sets), nearly all answer with one (response summary on most), and a route shows one or two read states - together about 3 of the 5 possible entries per tag set, so 60 % of the bound. The last two columns price the bound at 70 B per cache entry and at 300 B per meter, the low end of what a `SimpleMeterRegistry` summary holds (a Prometheus or OTLP histogram is kilobytes):

| Scenario | T | H | N | Bound | Typical (60 %) | Cache at bound | Registry at bound |
|---|---:|---:|---:|---:|---:|---:|---:|
| One unnamed client, base URL, expanded URIs only (no templates) | 0 | 1 | 1 | 5 | 3 | 350 B | ≥ 1.5 KB |
| One named client, base URL, ten templates | 10 | 1 | 1 | 55 | 33 | 3.9 KB | ≥ 17 KB |
| Three named clients, one base URL each, seven templates each | 7 | 1 | 3 | 120 | 72 | 8.4 KB | ≥ 36 KB |
| One client against four regional peers, fifteen templates | 15 | 4 | 1 | 320 | 192 | 22 KB | ≥ 96 KB |
| Gateway-shaped service: twenty named clients, ten templates each | 10 | 1 | 20 | 1 100 | 660 | 77 KB | ≥ 330 KB |
| Large application: twenty clients, twenty-five templates, two peers each | 25 | 2 | 20 | 5 200 | 3 120 | 364 KB | ≥ 1.6 MB |
| Pathological: the host tag built from caller data, ten thousand authorities seen | 5 | 10 000 | 1 | 300 000 | 180 000 | 21 MB | ≥ 90 MB |

Two things the table shows. First, in every row but the last, the factors are counts of things in the application's code or configuration - templates are string literals at call sites, peers are base URLs, names are set once per builder - so the number is fixed at deployment and does not move with request rate, payload, tenants or users; a service with a few downstreams sits in the tens to hundreds, a large application in the low thousands, at kilobytes to a few hundred kilobytes for the cache. Second, the last row is what the documented precondition on the host tag exists to prevent, and it is a registry problem before it is a cache problem: the 21 MB of cache sit next to at least 90 MB of meters, and the exporter shows the explosion long before either matters. The ratio of the two last columns - one to four or worse in every row - is the point: the cache never costs more than a fraction of what the host has already accepted for the meters themselves.

### 5.3 What an entry costs, against what its meter costs

An entry is a `ConcurrentHashMap` node (32 B: header, hash, key, value, next) plus the key (32 B: header and five compressed references) plus its share of the table array - about 70 B. The strings the key references are the ones the meter's `Meter.Id` holds (the builder is fed `key.uriTemplate`, `key.host`, `key.name`), so they are not counted twice. The 315-entry example costs about 22 KB; the few-thousand-entry one a few hundred KB.

The meter behind each entry costs more by an order of magnitude at least: a `SimpleMeterRegistry` summary holds its `Meter.Id` with `Tags`, a `DistributionStatisticConfig`, a `LongAdder`, a `DoubleAdder` and a `TimeWindowMax` with its ring buffer - several hundred bytes before any percentile or histogram configuration; a Prometheus or OTLP histogram with buckets is kilobytes. The cache therefore adds a few percent to what the host already pays for the meters, on every scale the meters themselves are tolerable at.

### 5.4 Why the cache deliberately has no bound of its own

Three reasons, in the order they matter:

1. **A bound would not limit anything.** The cardinality is the registry's, decided by the tags; the cache mirrors it. An eviction policy on the cache would evict entries whose meters stay in the registry and re-pay variant A for them - up to 448 B and 50 ns per sample on the evicted tag sets - while the registry keeps every meter. The host's cardinality problem, if it has one, would be exactly as large and now also slower.
2. **A bound would say the wrong thing.** A `maxEntries` on the cache reads as "the module limits body-meter cardinality", which only the tag folding does (`uriTag`) and the documented precondition on `host`. The place to control cardinality is the tag rule, where the registry benefits as well; a second knob on the cache would invite tuning the symptom.
3. **The monotone growth is the registry's own.** Micrometer registries do not evict meters either; an entry that exists once exists for the process lifetime, or until `MeterRegistry.remove`, which the listener honours. The cache and the registry grow in lockstep and shrink in lockstep; there is no state the cache can accumulate that the registry does not.

The pathological case is the same for both: a host that puts caller data into the `host` (a per-tenant authority, a user-supplied webhook) or records a per-call string with braces as a template creates a meter per value, and the exporter shows the explosion within minutes - the cache adds 70 B per meter to a problem measured in kilobytes per meter. It is the registry that must be protected there, by the documented rule, and that protection covers the cache for free.

## 6. What the result says, and what it does not

- It says the per-sample resolution was the largest avoidable allocation on the opt-in body-measurement path, and that it is gone: the owner is now within one small object of the meter itself.
- It says nothing about the emission as a whole. A measured exchange's emission formats a log line of several hundred bytes, opens two MDC scopes, renders up to two body captures and records the three samples; the samples' share of that was small before and is negligible now. A host that turns body measurement on pays for it in the meters' own state, not in the owner's bookkeeping.
- It says nothing about hosts whose `record` is expensive (a Prometheus histogram with many buckets, an OTLP exponential histogram). Both variants call the same `record`; the change moves nothing there.
- It does not measure the miss path (first sample per tag set per process): variant A plus one map insert, once. A host with a template explosion would pay it per new template - and would have a cardinality problem the `uri` folding exists to prevent, on the registry side long before the cache side.

## 7. Side observations

- The first run's 72 B/op (metadata block, "discarded run") is a general Kotlin point worth keeping: `computeIfAbsent` with a capturing lambda allocates the lambda on every call, not only on a miss. Where the hit path matters, a plain `get` first is the idiom; `getOrPut` on `ConcurrentHashMap` has the same lambda and, being non-atomic, would additionally need the `computeIfAbsent` anyway.
- JMH 1.37 on JDK 26 prints the `sun.misc.Unsafe::objectFieldOffset` deprecation warning at every fork start (from `org.openjdk.jmh.util.Utils`); it is JMH's, not the code under test's, and it does not affect the measurement. The `.mvn/jvm.config` flags the reactor uses for the same warning class do not apply to a plain `java -jar` run.
- SLF4J reports "No SLF4J providers were found" once per fork: the benchmark jar carries no logging backend, so the owner's `internalLog` is the NOP logger. Nothing in the measured paths logs on the happy path, so this changes nothing; a WARN on the fallback path would go nowhere, which is fine for a benchmark and would not be in a host.

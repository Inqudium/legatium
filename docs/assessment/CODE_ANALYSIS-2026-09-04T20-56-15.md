## 1. Executive summary

Legatium is a small (about 3,300 lines of production Kotlin), deliberately engineered pair of Spring Boot auto-configured client-logging libraries with an unusually explicit fail-open contract, injected time and id sources, and a lockstep-tested twin design. The production code is in good shape: no data loss, deadlock, resource leak or crash path was found in normal operation, every fail-open site is guarded, and the concurrency models of the two body captures are stated and honoured. The defects that exist sit at the seams with the framework rather than inside the module's own logic.

The single **High** finding is a misclassification on the reactive twin: Spring's own body-skip idiom — `bodyToMono(Void.class)`, `toEntity(Void.class)` and the unsupported-media-type path — drains a body-carrying response by cancelling the body `Flux`, and the filter records that framework-internal cancel as `adapter_outcome=cancelled` at WARN. Healthy fire-and-forget calls are logged as cancelled, the `cancelled` counter is inflated, and in `on-failure` body mode both bodies of such calls are written. The mechanism is verified in the Spring 7.0.9 and reactor-core 3.8.7 sources; no test in the suite exercises the idiom, so the defect is green across the build.

The **Medium** cluster has two production members and a test cluster. First, the documented "both twins in one application" deployment silently loses one twin's open-exchanges gauge: both twins register the same meter id on the same registry and Micrometer returns the first gauge, so the liveness signal the design relies on is blind for whichever twin is constructed second. Second, the reactive filter wires the exchange at assembly time, so a host filter that retries by resubscribing sees attempts 2..n unlogged, contrary to the class documentation. Third, on the blocking twin an `IOException` when *opening* the response body (and any runtime exception during the read) bypasses the failure report and the exchange is logged as `success`. Fourth, the opt-in body meters carry a `uri` tag that Spring fills with the *verbatim* string passed to `uri(String, ...)` — `uri("/things/" + id)` yields one tag value per id — and a caller-controlled `host` tag; both are commented as low-cardinality but are not.

On the test side the suite is deterministic and well isolated at the unit layer and would catch most deliberately introduced defects in the emission, outcome and masking logic. Its weaknesses are concentrated: the three Jazzer targets run in every build against an **empty input only**, because no seed corpus is checked in although CONTRIBUTING promises one; the interrupt-flag restoration of the shared fail-open guard is untested anywhere; the score-5 reactive filter is never driven through Spring's body-skip, a resubscription, or an empty completion; and the integration layer couples a single-threaded peer that sleeps 1.5 s to a 200 ms timeout applied even on happy-path calls, an order-dependent latent flake.

**Test verdict.** *Reliability as a safety net:* high at the unit layer (injected clock and ids, exact-message and exact-field assertions, genuinely hostile registries and appenders, a deterministic late-chunk race via a manual publisher); real defects would go red — with the one important exception that the High finding is not observable by any existing test. *Usage & coverage:* the pyramid has the right shape (fast unit tests carry the load, integration suites add engine evidence for four connectors and a real tracing bridge); risk paths at score 4/5 are covered except the framework-seam paths named above. *Most significant gaps & anomalies:*
- no test for `bodyToMono(Void)`/`toEntity(Void)`/unsupported media type, resubscription, or `Mono.empty()` from the connector on the reactive filter (finding 8);
- fuzz regression mode without a corpus — three "fuzz" tests per build that prove only "no crash on empty input" (finding 6);
- `failOpen`'s `InterruptedException` branch has zero executable evidence repo-wide (finding 7);
- a latent, order-dependent coupling between the single-dispatcher peer's 1.5 s sleep and the 200 ms happy-path timeouts in the connector suites (finding 9);
- roughly 55 % of the tests lack the rationale block the repository's own convention requires, and several test names or rationales claim more than their assertions check (pattern P1, findings 23–25, 29–30).

## 2. Scope & methodology

- **Modules analysed:** all three reactor modules, production and test code, completely. **Not analysed:** documentation, workflows, generated evidence pages, the shaded jars (the inlining is a packaging step; the source module is the subject).
- **Test code in scope:** yes — both as a risk indicator and as an analysis subject; the test-specific heuristics were applied to every test class.
- **Detected stack:** Spring Boot 4.1.1 / Spring Framework 7.0.9. Two paradigms side by side: the RestClient twin is **blocking** (a `ClientHttpRequestInterceptor`, thread-local MDC around the wire call, `InputStream` tee, emission at `close()`); the WebClient twin is **reactive** (an `ExchangeFilterFunction` on Reactor, `DataBuffer` tee through a `ClientHttpRequestDecorator`, emission at the body's terminal signal). No Kotlin coroutines in production code (the coroutine caller path is documented as the same filter). No virtual-thread configuration in the modules; the id generator and masker are written with virtual threads in mind (no thread-locals, no per-call `SecureRandom`). No persistence, no messaging.
- **Language:** Kotlin 2.4.10 with `-Xjsr305=strict`; Java only for the Jazzer fuzz targets. Interop surface: Spring platform types are handled with explicit nullability throughout; no `!!` in production code.
- **Existing static analysis:** ktlint, CodeQL, Scorecard, OSV, Jazzer regression mode. No detekt/SpotBugs/ArchUnit/Sonar (see the environment block).
- **Local verification:** the build and the full test suite were run green at this commit before the analysis. No reproducing test was written; every Medium+ finding is instead backed by the framework source lines cited in the finding.
- **Known limitations / blind spots:** (a) the "both twins in one application" deployment cannot be exercised inside the reactor (the modules do not depend on each other), so finding 2 rests on code reading plus the Micrometer source; (b) engine behaviours were verified for the four Spring-shipped connectors and the JDK/Apache request factories only; (c) the Tarpit-based connect-timeout tests are Linux-specific by design, which is documented in the helper and not repeated as a finding; (d) security aspects (log injection, masking strength) are noted where they overlap with robustness but not explored — that is the security audit's topic.

### 🟠 High

- [x] 1. [./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ClientRequestLoggingFilter.kt:175 and ./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ExchangeLogEmitter.kt:162] {High} {Confidence: high — mechanism verified in spring-webflux 7.0.9 `BodyExtractors.java:266-276` and reactor-core 3.8.7 `FluxTakeWhile.java:94-99`; not executed} {reactive / correctness} Spring's body-skip idiom is logged as `adapter_outcome=cancelled`
  - Symptom → cause: `retrieve().bodyToMono(Void.class)`, `toEntity(Void.class)`, `bodyToFlux(Void.class)` and the `UnsupportedMediaTypeException` path on a response that carries at least one body buffer produce a WARN line with `adapter_outcome=cancelled`. `BodyExtractors.skipBodyAsMono` drains a `ClientHttpResponse` body through `consumeAndCancel`, which is `message.getBody().takeWhile(buffer -> { release(buffer); return false; })`; `FluxTakeWhile.onNext` on a false predicate calls `s.cancel()` then `onComplete()`. The response the filter hands back is `mutate()`d (a `BuiltClientHttpResponse`, still a `ClientHttpResponse`), so the tee chain in `onResponse` receives that CANCEL: `.doOnCancel { exchange.cancelled = true }` (filter:175), and the emitter's matrix resolves `cancelled -> Level.WARN to OUTCOME_CANCELLED` (emitter:162) before the success branch (emitter:164).
  - Triggering condition: always, for these standard `WebClient` idioms whenever the peer sends a body (a 204 or an empty body completes normally and is unaffected; `toBodilessEntity()` drains via `releaseBody()` and is unaffected).
  - Impact: wrong outcome and level for healthy calls; `adapter.logging.events{outcome=cancelled}` and the documented "cancelled share" signal are inflated; in `on-failure` body mode the gate `failed = outcome != OUTCOME_SUCCESS || status in 400..499` (emitter:194) becomes true, so **both bodies of every such successful call are written** — defeating the ADR-0006 volume promise and widening the exposure of payloads; on the unsupported-media-type path the caller sees an error while the line says `cancelled` without a cause.
  - Fix strategy: distinguish a consumer-initiated body skip from a real cancellation — for example, treat a body CANCEL on an exchange whose response has already arrived as `success` with read state `partial` unless the outer `Mono` was cancelled too, and pin the four idioms with stub-driven unit tests (a body-carrying stub response and `bodyToMono(Void::class.java)` suffices; all paths are synchronous).
  - **Fixed (2026-09-04):** `ObservedBody` (new operator on the response body) distinguishes a cancel issued from within the consumer's own `onNext` delivery (Spring's body skip, a `take`) - exchange `success`, read state `partial` - from an out-of-band cancel (`cancelled`). Pinned by four new filter tests (Spring skip via `bodyToMono(Void)`, `take(1)` with the partial read-state counter, out-of-band cancel, `next()`).

### 🟡 Medium

- [x] 2. [./legatium-restclient-logging/src/main/kotlin/eu/inqudium/legatium/restclient/logging/ClientLoggingMetrics.kt:104 and ./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ClientLoggingMetrics.kt:104] {Medium} {Confidence: high — Micrometer `MeterRegistry.registerMeterIfNecessary` returns the existing meter for an identical id; both classes use the identical id `adapter.logging.exchanges.open` without a distinguishing tag} {correctness} Both twins in one application: the second twin's open-exchanges gauge is silently dropped
  - Symptom → cause: the documented deployment "an application may carry both twins" (`./README.md:98`, ADR-0003) registers `Gauge.builder(OPEN_EXCHANGES_METER, open) { it.get().toDouble() }` twice on the same host registry — once per twin, each bound to its own `AtomicLong`. Micrometer deduplicates by id and returns the first gauge; the second registration neither throws (so `registerOrFallback`, which only reacts to exceptions, does not fall back) nor binds. The class KDoc describes precisely this failure for a second instance of the *same* class and prevents it with the per-registry cache `perRegistry` — but that cache is per class, and the two twins are two classes with two caches.
  - Triggering condition: both jars on the classpath with one `MeterRegistry`; whichever twin constructs its metrics owner second loses its gauge.
  - Impact: the liveness signal the design depends on ("a growing baseline means events are lost silently") is blind for one twin; a never-closed response or a never-subscribed body in that twin is invisible while the counters still merge, so an operator sees a healthy baseline. No test can currently observe this (see limitation (a)).
  - Fix strategy: give the gauge a `stack` (or `client`) tag so the ids differ and both gauges bind, or resolve the open-exchange holder by registry through a lookup of the existing meter and share it; document the choice in the both-twins paragraph.
  - **Fixed (2026-09-04):** The open-exchanges gauge carries a `client` tag (`restclient` / `webclient`) in both metrics classes, so the two ids differ and both gauges bind; documented in both guides' §5.4 and pinned by a metrics test per twin.

- [x] 3. [./legatium-webclient-logging/src/main/kotlin/eu/inqudium/legatium/webclient/logging/ClientRequestLoggingFilter.kt:128-139] {Medium} {Confidence: medium} {reactive / correctness} Wiring runs at assembly time; a resubscribing retry logs attempt 1 only
  - Symptom → cause: `wireOrNull(request)` (128), the arrival line (131) and `metrics.exchangeOpened()` (312, inside wiring) execute when `filter()` is *invoked*; only the connector call is deferred (`Mono.defer { next.exchange(wiring.request) }`, 138). An outer filter that retries by resubscribing the returned `Mono` (`.retry(n)`, `.retryWhen(...)`, a `RetryOperator` via `transformDeferred`) re-runs the connector with the same `Exchange`. After attempt 1 completed, `state` is `COMPLETED`, so attempt 2's `compareAndSet(OPEN, RESPONDED)` (163) fails and every later `complete()` returns at the guard (208). The class KDoc promises the opposite: "once per attempt of a retrying filter" (56).
  - Triggering condition: only with a host filter ordered outside this one that retries by resubscription rather than by re-entering the filter chain (a caller-side `.retry()` on the `WebClient` result re-enters the chain and is fine).

  - Fix strategy: move the `Exchange` creation, arrival line and gauge open inside a `Mono.defer` so wiring runs once per subscription, and add a unit test that subscribes the filter's `Mono` twice and expects two lines.
  - **Fixed (2026-09-04):** The whole filter body runs inside `Mono.defer` - wiring, arrival line and gauge open per subscription; an assembly-time exception is routed into the chain as `Mono.error`. Pinned by a resubscription test expecting two lines.

- [x] 4. [./legatium-restclient-logging/src/main/kotlin/eu/inqudium/legatium/restclient/logging/CapturingClientHttpResponse.kt:51] {Medium} {Confidence: medium} {correctness} An `IOException` while opening the response body is logged as `success`
  - Symptom → cause: `ClientHttpResponse.getBody()` is declared `throws IOException`. The tee guards the `read` calls (`guarded { real.read() }`, 55/69, reporting through `onReadFailure`), but the initial `val real = delegate.body` (51) is unguarded, so an exception there propagates to the application while `exchange.failure` stays null; the client's `finally` then closes the response and the exchange is classified `success` with the received status. Likewise a `RuntimeException` thrown by `real.read()` (an `UncheckedIOException`, an engine-specific wrapper) is invisible, because `guarded` catches `IOException` only (82-88).
  - Triggering condition: only edge case — the engine fails when opening the body stream (connection dropped between status line and body, a decompression setup failure) or throws a runtime exception mid-read.
  - Impact: wrong `adapter_outcome` on exactly the calls the outcome exists for; the `events{outcome}` counter misattributes them; no fail-open count either.
  - Fix strategy: route `delegate.body` through the same guard as the reads and widen the guard to `Exception` (report, then rethrow unchanged), since any throw during the application's read is a failed exchange.
  - **Fixed (2026-09-04):** `CapturingClientHttpResponse` guards the opening `delegate.body` call like a read and the guard now covers any `Exception`; `onReadFailure` takes an `Exception`. Pinned by two interceptor tests (body cannot be opened; unchecked exception mid-read).

## 6. Systemic patterns

- **P1 — Rationale block missing (documented convention deviation).** `./CONTRIBUTING.md:96-98` requires the three-line `What is tested:` / `Success criteria:` / `Why it matters:` block at the top of every test body; it is also what the generated evidence page shows. Counted via `grep -c '@Test'` vs `grep -c 'What is tested:'` over `*/src/test/**/*.kt`: legatium-common 32 of 62, legatium-restclient-logging 41 of 89, legatium-webclient-logging 36 of 91 — **109 of 242 tests (45 %) carry the block, 133 do not.** Every test does have Given/When/Then stage comments. Low per occurrence, listed once. Related: four tests whose name, Javadoc or rationale asserts more than the code checks (findings 22, 23, 25, 30).
- **P2 — Fail-open boundary is `Exception`, never `Throwable`.** 17 `catch (e: Exception)` / `catch (ignored: Exception)` sites across the three modules' production code (`grep -c` over `*/src/main/**/*.kt`) plus `failOpen`/`reportQuietly`/`MdcScope`. - **P3 — Real-time dependence in the integration layer.** About 7 sites: both `PeerServer.kt:58` (`Thread.sleep(1_500)` on a single dispatcher thread), `ConnectorContract.kt:205` (`SHORT` used by four scenarios × four engines), `ClientRequestLoggingFilterIntegrationTest.kt:177,216` (200 ms), `ClientRequestLoggingInterceptorIntegrationTest.kt` (JDK read timeout), and the kernel-dependent `Tarpit`.

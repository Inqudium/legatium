## 1. Executive summary

This is the seventh defect analysis of the codebase, one day after the sixth. Between the previous report (`DEFECT_ANALYSIS-2026-09-20T20-38-01`, commit `14cbef9`) and this commit eight pull requests landed: the fixes for that report's seventeen findings (#49), a third comment-audit round with its fixes (#50, #51), the comment-prefix vocabulary of ADR-0013 with a blame-ignore file (#52), two CI guards against drifting comment citations (#53), the last comment pass and a rewrap (#54, #55), and one production refactor: the twins' private `newCaptures()`/`captureFor()` pair became the shared `BodyCaptures.of(properties, ::BoundedBodyCapture)` in `legatium-common` (#56). The production diff outside comments is small and was read line by line: the interceptor's call scope now opens inside the `try` (a nullable local), both reactive operators complete the exchange in a `finally` around the downstream's terminal call, `AmbientContextRestorer.detect` checks presence on both loaders, `cacheBodyMeter` refuses a meter whose id no longer carries the key's tag values, and `BodyCaptures` reproduces the deleted decision table exactly. **All seventeen carried findings are fixed and effective** in the sense that the mutation each of them pinned now goes red - with one half-exception: finding 11's resolution note claims the JDK client is released bounded "in both twins", but the blocking twin's Boot-builder suite kept two `close()` sites the finding had named (finding 1 below). The twins' lifecycle code - bounded body capture, exactly-once completion, the new `finally` shape, fail-open guards, additive MDC and Reactor-context restoration, twin symmetry - was re-read in full and is sound.

**No Critical, no High and no Medium finding.** Six Low findings in three groups. Two are unfinished business of the last round: the half-applied JDK release (finding 1) and the reactive module guide, whose lifecycle diagram and emission table (§2.3, §2.4, §4.5) still describe the `doOnCancel`/`doFinally` body chain that the `ObservedBody` operator replaced on 2026-09-04 - a description that contradicts the guide's own §2.1 and §4.2 and would, taken literally, classify every body cancel as `cancelled` (finding 6). Three are coverage gaps at documented rules in the P5 shape, two of them in code that changed since the last report: the new `BodyCapturesTest` claims in its own rationale that the measuring switches are irrelevant once a body mode captures, yet never sets them, so the precedence of the shared rule is pinned only incidentally by one freeze test of the reactive twin (finding 3); the new `describes` check is deliberately lenient towards tag-ADDING filters so that Boot's `management.metrics.tags.*` do not defeat the cache, and no test would notice an over-strict rewrite that silently disables the cache in nearly every real host (finding 4); and the order rule of both reactive operators - hand the terminal signal on first, complete the exchange afterwards, so the duration covers the decoder's join as the blocking twin's occupancy does - survives being swapped in all four terminal callbacks with a green suite (finding 5). The sixth is the blocking tee's `mark()` forwarding to the capture, which every test takes at stream position 0, where the capture's default mark already sits (finding 2).

**Test verdict.** *Reliability as a safety net:* high across all three modules - the score-5 suites go red under the mutation experiments applied here (the call scope hoisted above the `try`, each `finally` removed, `upstream.cancel()` deleted in either operator, the scope nesting swapped, the `linkedThrough` check dropped, the `Mono` body demoted, `describes` reverted, the rollback's `andThen` moved out of the `try`, the vocabulary guard made null-safe), fault injection is real (a JVM-globally armed adapter that dies with a `LinkageError`, a delegate refusing status text, headers and `available`, a subscriber throwing from both terminal signals with a hook that catches either surfacing route, a folding `MeterFilter`), and the risky logic is checked deterministically with an injected clock and pinned ids; the retry-context test is order-independent now. *Usage & coverage:* the pyramid is base-heavy - 437 unit and contract test methods plus 4 fuzz targets carry the behaviour (144+6+3, 148+1+1, 145 declared per module, plus 3 in the smoke test; the engine matrices multiply the contract methods); nine real-engine suites, Boot-builder and Brave tracing integrations and the consumer smoke test verify the seams; every cross-thread wait is bounded except the two `HttpClient.close()` sites of finding 1. *Most significant gaps and anomalies:*

- Four documented rules have no test that would catch their removal, three of them in code or tests written since the last report (findings 2-5, pattern P5).
- The reactive guide's lifecycle section describes an emission mechanism that no longer exists and that the suite explicitly rules out (finding 6).
- The blocking twin's Boot-builder suite still owns two unbounded engine releases its own fixture KDoc forbids (finding 1).

## 2. Scope & methodology

**Modules and roles.** `./legatium-common/` holds the byte-identical shared code the two twins inline through Shade (ADR-0003): the bounded buffer, properties and their origins, header selection and masking, activation, identity (`traceparent`, correlation header, counting id), classification, the metrics owner with the body-meter cache, the MDC scope with the shared install/rollback/restore functions, timeout classification, the observation-wiring report and - new since `14cbef9` - the capture rule `BodyCaptures`. `./legatium-restclient-logging/` is the blocking twin (a `ClientHttpRequestInterceptor` whose emission point is `ClientHttpResponse.close()`), `./legatium-webclient-logging/` the reactive twin (an `ExchangeFilterFunction` with two hand-written Reactor operators whose emission point is the body publisher's terminal signal). `./consumer-smoke/` checks the shaded jars as a consumer sees them; `./benchmarks/` holds JMH measurements of the buffer and the body-meter cache.

**Stack detected.** Spring Boot 4.1.1 on Spring Framework 7.0.9, Micrometer 1.17.1; both blocking (`RestClient`/`RestTemplate`) and reactive (`WebClient`, Reactor) client stacks; no coroutines; virtual threads neither configured nor assumed (the one `synchronized` block in production code guards a `WeakHashMap` lookup at owner creation, never a blocking call); no persistence, messaging, scheduling or controllers - this is a library, whose entry points are the interceptor, the filter, two auto-configurations, three customizers and one `SmartInitializingSingleton` per twin. Optional dependencies: `spring-boot-restclient`/`spring-boot-webclient` (customizers), `io.micrometer:context-propagation` (ADR-0010 restoration).

**Test code in scope: yes.** The three modules carry 153, 150 and 145 declared test methods (by annotation: 144 `@Test` + 6 `@ParameterizedTest` + 3 `@FuzzTest`; 148 `@Test` + 1 `@ParameterizedTest` + 1 `@FuzzTest`; 145 `@Test`), plus 3 in `consumer-smoke`; the blocking contract's 6 methods run in five engine suites and the reactive contract's 5 in four. Test-quality heuristics were applied to every non-trivial test (evidential value by mutation thought experiment against the production code, determinism, isolation, risk-path coverage, sham concurrency, resource lifecycle, convention deviations against `./CONTRIBUTING.md`).
